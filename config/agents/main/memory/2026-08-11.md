### Race fix 内容（P0 fixes）
1. **`std::atomic<GstElement*> appsrc{nullptr}`** — 64-bit ptr 跨线程读写用 atomic（GMainLoop 设 / 主线程读）
2. **`std::atomic<int> client_count{0}`** — 替代 `bool client_connected`，可同时多 client
3. **`std::atomic<bool> appsrc_wants_data{false}`** — appsrc signal control 也 atomic
4. **`std::atomic<bool> media_prepared{false}`** — 配对 prepared/unprepared，8-08 调试发现 unprepare 在 connect 后立即误触发
5. **`on_media_prepared` callback** + on_media_unprepared 用 `media_prepared.exchange(false)` 判断是否真断开
6. **max-bytes=10000000, max-buffers=10** — launch string 默认 max-bytes=200000，1 个 BGR frame (921600 bytes) 超过 → enough-data 立即触发 → pipeline 不消费 → 死锁。**这是 race fix 的根因之一**
7. **`g_preroll_pushed` flag** + `on_need_data_preroll` — 每个 media instance 重新 preroll 黑帧
8. **capsfilter I420** 强制保留（8-09 修过）

### ⚠️ 发现：client_count 是 media instance 计数，不是 RTSP client 计数
```cpp
// on_media_configure: RTSP server media-configure signal callback
g_state.appsrc.store(appsrc);
int count = g_state.client_count.fetch_add(1) + 1;  // 共享 media 只触发一次
```
- 因为 RTSP media factory 默认是 shared (一个 media 多个 client 共享)
- 所以 4 client 实际是共享同一个 media, client_count 永远 = 1
- 要真正计 RTSP client 数量，需要监听 RTSP client hooks (`accept-client` / `closed-client`)
- **不影响功能, 只是日志显示 client=1 不准**

### ⚠️ 内存没回 baseline (84M → 211M, +127MB)
- 4 个 client session 共占 ~127MB (~32MB/client)
- 断开后 30s+ 没回收, 可能:
  - glibc heap fragmentation (常见, 无害)
  - RTSP server per-session buffer 没主动 free
  - 微小 leak (需长时间运行确认)
- **不影响稳定性和性能**, 标记观察项
