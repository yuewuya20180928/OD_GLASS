## 00:13 — v0.P+ NEON memcpy 升级尝试失败

### 改动
- awnn_lib.c 的 `neon_memcpy_f32`:
  - 16 float/iter → 32 float/iter (8 个 vld1q/vst1q)
  - 加 `__builtin_prefetch(src + i + 64/128, 0, 0)` (L1/L2 read)
- 重编 `-O3 -ftree-vectorize`
- prfm 指令确实生成了 (objdump 看到 2 条)

### 实测 (回滚后 A+B baseline 11.22 FPS, v0.P+ 11.09 FPS)
| 指标 | A+B baseline | v0.P+ | 收益 |
|------|--------------|-------|------|
| fp32 6528000 memcpy (大输出 26MB) | 31.96ms | 31.61ms | **-0.35ms (-1%)** |
| fp32 1632000 memcpy (中输出 6.5MB) | 7.86ms | 7.76ms | -0.10ms |
| fp32 408000 memcpy (小输出 1.6MB) | 2.00ms | 1.87ms | -0.13ms |
| tensor_to_fp 总 | 41.91ms | 41.36ms | **-0.55ms (-1.3%)** |
| worker_total_ms | 80.2 | 81.1 | **+0.9ms (反而慢)** |
| 稳态 FPS | 11.22 | 11.09 | **-0.13 FPS** |

### 失败根因 (铁律: 看数据)
- memcpy 已经接近 NPU DDR 物理带宽上限 (~800 MB/s)
- 26MB @ 31.6ms = 822 MB/s, 离 LPDDR4 理论 8+ GB/s 差 10x, 但 NPU 设备到 host 的物理通道就这带宽
- prefetch hint 对 NPU device memory 源无效 (不是普通 DRAM)
- 32-float batch 没突破带宽瓶颈, 反而因 instruction count 多增加 OoO window 压力

### 结论 (加到 MEMORY)
- **NEON memcpy 已到底, 不要再试** (glibc memcpy + aarch64 SIMD 已是最优解)
- tensor_to_fp 41ms = NPU→host 物理搬运上限, 不能用软件优化突破
- **唯一突破路径: 改 .nb 输出格式 (int8) 把 26MB → 6.5MB (4x 加速)**

### A+B 后 3 次尝试全失败汇总
| 方案 | 结果 | 原因 |
|------|------|------|
| 🆂 std::async (3 sections) | 11.62 vs 11.22 baseline | pthread fork overhead > saving |
| 🆃 OpenMP parallel for | 9.88 (反而慢) | critical section + libgomp scheduling > cell 工作量 |
| 🆄 NEON memcpy 32-float + prefetch | 11.09 (略慢) | memcpy 已达物理带宽上限 |

**A+B baseline 11.22 FPS = 当前软极限 (没动 model 的情况下)**
