## 2026-08-08 08:56 — 压测 v31 + 发现内存泄漏 + OOM kill 🐛

### 压测方法
- baseline: 0 client, fps=25.00 稳态
- 4 client 并发 gst-launch RTSP 拉流 (60s)
- 监控 FPS + RSS + swap + CPU

### 压测结果
| 阶段 | client | FPS | grab ms | od ms | push ms | RSS | swap |
|---|---|---|---|---|---|---|---|
| baseline | no | 25.00 | 0.1 | 0.1 | 0.0 | 65MB | 0 |
| 4 client (30s) | yes×4 | 25.00 | 0.1 | 0.1 | 0.0 | 1015MB | 739MB |
| OOM 后重启 | no | 25.00 | 0.7 | 0.6 | 0.0 | 65MB | 0 |

**FPS 在任何负载下都是 25.00 稳态** — NPU/USB 完全 OK
**但 RSS 从 65MB → 1015MB + swap 739MB → 触发 cgroup OOM kill**

### OOM 现场 (dmesg)
```
[ 693.577374] v31_v4l2_od_rts invoked oom-killer
[ 693.577594] oom-kill:constraint=CONSTRAINT_MEMCG
[ 693.577629] Memory cgroup out of memory: Killed process 1793 
              total-vm:5547520kB anon-rss:1038788kB swapents:757120kB
```
- MemoryMax=1G cgroup 限制 (从 service unit)
- anon-rss: 1038788kB = 1015MB
- swapents: 757120kB = 739MB
- → kernel cgroup OOM killer 杀掉 PID 1793
- → systemd Restart=on-failure 自动重启为 PID 2508

### 根因: v31 source 有内存泄漏 (跟 RTSP client 数量相关)
- main loop 每帧 `malloc(frame_bytes=921KB)` for each client when `client_connected=true`
- appsrc `max-bytes=0` (无界)
- glibc malloc arena 不归还内存给 OS → RSS 持续涨
- **没 client 时不分配 → RSS 不涨** (验证: PID 2508 fresh = 65MB)

### 修法选项
A. **快修**: service unit `MemoryMax=2G` (从 1G), 让 OOM 阈值提高
B. **appsrc 限速**: pipeline 改 `max-bytes=10000000` (10MB queue), 超出会 back-pressure / 丢帧
C. **代码层**: v31 source 用 buffer pool (预分配 N 个 frame buffer 循环复用), 避免 malloc
D. **glibc trim**: 周期调 `malloc_trim(0)` 还内存给 OS

### 教训 (新铁律)
- **【铁律】appsrc max-bytes=0 + per-frame malloc = 内存炸弹** 
  - 每秒 25 frame × 921KB × 4 client × 60s = 5.5GB 累积分配
  - glibc arena 不归还 → RSS 单调涨
  - 必须设 `max-bytes` 或用 buffer pool
- **【铁律】MemoryMax=1G 对 4 client RTSP server 不够用**
  - v31 base 65MB + appsrc buffer queue 1GB+ → OOM 不可避免
  - 需要 2-3G MemoryMax, 或修代码限速

### 待办 (今晚)
- 跟老板确认 A 方案: MemoryMax=2G (最快)
- 中长期: B+C 修 v31 source (buffer pool + max-bytes)

## 2026-08-08 09:43 — 🎉 单 client OOM 修复成功！signal control 方案 ✅

### 修复过程（多版迭代）
1. **v1: appsrc max-bytes=10MB + max-buffers=2 + unref on FLOW_ERROR** — ❌ 失败 (RSS 仍涨 23MB/s)
2. **v2: + block=true** — ⚠️ 内存稳 (~80MB) 但 FPS 降到 12-14 (encoder 瓶颈)
3. **v3: block=false + max-buffers=1** — ❌ 失败 (appsrc max-bytes/max-buffers 看起来不生效)
4. **v4: cur_buffers check via g_object_get** — ❌ 失败 (current-level-buffers 不准确, 仍涨 23MB/s)
5. **v5: appsrc signal control (need-data/enough-data + media unprepared)** — ✅ **完美成功**

### v5 修复方案 (workspace 备份)
1. 加 `appsrc_wants_data` 标志 (默认 true)
2. `on_need_data` signal handler: 设 `appsrc_wants_data=true`
3. `on_enough_data` signal handler: 设 `appsrc_wants_data=false`
4. `on_media_unprepared` signal handler: 设 `client_connected=false, appsrc=NULL`
5. main loop: 只在 `client_connected && appsrc && appsrc_wants_data` 时 push

### 关键发现
- **appsrc max-bytes/max-buffers 在 launch string + g_object_set 都不生效** (板端实测)
- **current-level-buffers 也不准确** (有时候 appsrc 有 buffer 但返回 0)
- **唯一可靠的边界控制**: appsrc 信号 (need-data/enough-data)
- **client_connected 必须用 media-unprepared signal 设回 false** (不能永远 true)

### 新铁律 (重要!)
- **【铁律】appsrc max-bytes/max-buffers 在 radxa-a733 GStreamer 不生效**
  - 必须用 appsrc signal (need-data/enough-data) 控制 push
  - 不能用 launch string 设, 也不能用 g_object_set 设
- **【铁律】v31 client_connected 必须用 media-unprepared signal 重置**
  - client_connected 永不复位 → main loop 持续 push → appsrc 持续累积 → RSS 爆炸

### 关键发现 (10:38) — 终极修复
**"main loop 阻塞主线程"** 是元凶:
- v31 之前 `g_thread_new("gst-loop", g_main_loop_run, loop)` — 把 GMainLoop 单独跑一个 thread
- 结果 GStreamer RTSP server 在那个 thread 处理, 但 media-configure 触发时 main C++ 线程还没初始化 appsrc
- 修复: 改成 `g_main_loop_run(loop)` 在主线程 (不 g_thread_new)
- 加 `stream-type=2` (appsrc 接受 random access timestamps)
- videoconvert 后面加 caps `video/x-raw,format=I420,width=640,height=480,framerate=20/1`
- on_media_configure 加 50ms 延时 (等 pipeline state READY)

### 终极 pipeline (work 版)

### 新铁律 (重要!)
- **【铁律】GStreamer RTSP server 的 GMainLoop 必须跑主线程 (不要 g_thread_new)**
  - GstRTSPMediaFactory media-configure 是 sync invoke, 必须在主线程
  - 用 g_thread_new 是 anti-pattern, 状态机混乱
- **【铁律】x264enc 默认 baseline profile 不支持 4:4:4** (BGR 是 4:4:4)
  - 必须显式 `profile=high` (或 main/high10)
  - 不显式 → silent 失败, PC 端 503
- **【铁律】appsrc 必须用 stream-type=2 接受 random timestamps**
  - default stream-type=0 (seek) 严格要求 uniform timing
  - stream-type=2 (random-access) 接受任意时间戳
- **【铁律】videoconvert 必须显式指定下游 caps (I420 + width/height/framerate)**
  - appsrc caps 写完整, videoconvert 还要写 I420 caps
  - x264enc 需要明确 input format, 没 caps = 静默失败
- **【铁律】media-configure 回调要 50ms 延时等 pipeline state READY**
  - 立即拿到 appsrc 指针, 此时 element 还在 NULL → READY 转换
  - 50ms 延后稳定
