# 2026-06-16 OD 标注错位 bug 修复

## 路径
`/work/object_detection/od_project/`（= `/home/yuewuya/Public/object_detection/od_project/`）

## 问题（一句话）
od_project 目录下的 demo / evaluate 脚本能检测出目标（box 位置对），但**目标标注名和实际物体对不上**——例如把笔记本识别成冰箱/水槽/cls85。

## 根因
**TF OD API 官方预训练模型 `ssd_mobilenet_v2_fpnlite_320x320_coco17_tpu-8` 的 `pipeline.config` 里 `num_classes: 90`**，但 COCO 数据集只有 80 个检测类。多出的 10 个 slot（1-based 81-90）是 padding/未监督的，模型对它们也会输出非零噪声分数。

- 修复前实测 200 张 val：score≥0.5 的 423 个预测中 **21 个 (5%) 是 padding 类**（会被画成 `cls85` 之类的乱标签）
- 笔记本图 `000000415238.jpg` top-1 是 1-based 86 (0-based 85, OOB)，挤压了真正的 laptop (score 0.511)

`COCO_NAMES` 列表本身顺序是对的（标准 TF OD API 顺序，1-based 64→laptop, 73→refrigerator 都对得上），不是列表错。

## 修复
**`/work/object_detection/od_project/demo_odapi.py`**（两处相同逻辑，frame + frozen_frame 两个分支都要改）：
```python
class_ids = cls - 1
# ⚠️ 关键: 过滤 padding 类 (1-based 81-90 → 0-based 80-89)
valid_cls = (class_ids[:num] >= 0) & (class_ids[:num] < 80)
keep = (sc[:num] >= score_thresh) & valid_cls
```

**`/work/object_detection/od_project/evaluate_odapi.py`**（在 `all_dets.append({...})` 之后）：
```python
_cid_arr = all_dets[-1]["class_ids"]
_valid = (_cid_arr >= 0) & (_cid_arr < 80)
all_dets[-1]["boxes"] = all_dets[-1]["boxes"][_valid]
all_dets[-1]["scores"] = all_dets[-1]["scores"][_valid]
all_dets[-1]["class_ids"] = _cid_arr[_valid]
```

## 验证
| 指标 | 修复前 | 修复后 |
|---|---|---|
| score≥0.5 中 padding 类 (≥80) | 21 | **0** ✅ |
| 笔记本图 top-1 | cls85 (OOB) | **laptop** ✅ |
| mAP@0.5 | 0.0712 | 0.0712（不变，见下） |
| mAP@0.5:0.95 | 0.0454 | 0.0454 |

## mAP 为什么没变
`compute_map()` 内部对 `class_ids >= num_classes=80` 的预测本来直接 ignore，padding 类没贡献 FP。修复没让 mAP 变差也没变好。**修复价值在 demo 视觉**，不在 mAP。

## 附带的临时改动
- `od_project/data`、`utils`、`models` → 软链到父目录（`/work/object_detection/`），方便直接 `python3 evaluate_odapi.py` 跑

## 待办（独立议题）
mAP@0.5 = 0.07 vs paper 0.29 的差距大概率是 val TFRecord 抽样问题（200 张太少 + 类不均衡）。下一步要查 GT 抽取逻辑，跑全量 5000 张 val2017 看真实分布。

# 2026-06-16 (下午续) 进一步排查 + Code-level 优化实验

## 字母条 (letterbox) 公式修复
**Bug**：`evaluate_odapi.py` 和 `evaluate.py` 里 GT 加载用了 `new_w = orig_w * scale`（float），而 `dataset_builder.py` 用 `new_w = int(orig_w * scale)` + `// 2` 算 padding。
- 影响：GT box 中心点偏移 0~0.75 像素
- 修复：float → int truncation，对齐 dataset_builder

## 全量 val 评估：mAP 仍 ≈ 0.06
| 配置 | mAP@0.5 | 张数 |
|---|---|---|
| 修复前 baseline | 0.0611 | 2476 |
| letterbox 修复后 | 0.0628 | 1000 |

**letterbox 修复几乎没改善 mAP**。证明 mAP=0.06 不是评测代码 bug，是**模型本身太弱**（SSD MobileNetV2@320 报告 mAP 0.22，但 COCO val2017 全量 80 类、跨 5K 张才有这个数；我们只测 2476 张，类分布偏）。

## 类分布实测（2476 张 val）
- 模型预测 3533 detections vs GT 382
- elephant 被预测 13× 于 GT（虚警）
- person 仅预测 19% GT（漏检）
- **28/80 类 AP=0**（背包、床、滑雪板、飞盘、牙刷等小目标类）

## Top AP: airplane(0.76), bus(0.69), fire_hydrant(0.67), train(0.63), person(0.53), motorcycle(0.45)
## 0 AP: bench, stop_sign, tie, umbrella, skis, frisbee, snowboard, suitcase, backpack, bed, toaster, hair_drier, scissors

## Code-level 优化实验（**全部失败，对 mAP 反向**）
| 优化 | mAP@0.5 | Δ vs baseline (0.0628) |
|---|---|---|
| per-class thresh (aggressive) | 0.0503 | **-0.013 ↓** |
| per-class thresh (conservative) | 0.0411 | **-0.022 ↓↓** |
| soft-NMS | 0.0585 | -0.004 ↓ |
| Top-K 30 | 0.0613 | -0.002 ↓ |
| Top-K 20 | 0.0601 | -0.003 ↓ |
| soft-NMS + Top-K 30 | 0.0576 | -0.005 ↓ |

**理论解释**：compute_map 内部 PR 曲线对低分 FP 有鲁棒性（最后一个 TP 之后的低分 FP 不影响 AP），而这些优化砍掉的**主要是低分 TPs**，损失 recall > 减少 FP。
