## 1. 技术架构 (数据流)

```
1 路可见光 sensor (MIPI-CSI, 1080p@60)
  → ISP + EIS (可关)
  → 缩放: 1080p → 800×600 (显示分辨率, 同时作为 OD 输入源)
                              ├→ MIPI-DSI → 光机 → [一拖二分光] → 2 片波导 → 双目
                              └→ letterbox 800×600 → 640×640 → YOLOv5 INT8 80 类 OD
                                                      → decode + NMS
                                                      → 框坐标映射回 800×600
                                                      → 画框 → 并入 800×600 显示帧 → MIPI-DSI
```

## 3. 关键指标预算 (**全部为我推算, 未实测, 不可作为决策依据**)

### 3.1 ISP 吞吐 (基于公开 spec 反推)

公开 spec: 4K@30fps 单路 output ≈ 250 MP/s

| 配置 | ISP 吞吐 | 占比 | 风险 |
|---|---|---|---|
| A. 1080p@60 **关 EIS** (基线) | 124.4 MP/s | **49.8%** | 中等, 可行 |
| B. 1080p@60 开 EIS | +帧间 load | ~70-80% | 紧张, 需原厂书面确认 |
| C. 1080p@30 关 EIS | 62.2 MP/s | 24.9% | 低, 保守方案 |

**风险**: 1080p@60 + EIS 在 ARS45 上是**未验证组合** (公开只有 1080p@30fps EIS 功耗数据 <300mW)

### 3.2 NPU 推理 (最大未知数)

**目标模型**: yolov5s INT8 @640×640, 需 ≤ **16.67ms** (60fps 帧周期) 才成立 640×640@60 配置

**横向参照** (Rockchip 官方 model_zoo, yolov5s INT8 @640×640):

| 芯片 | 标称 | fps | 延迟 |
|---|---|---|---|
| RK3588 (单核) | 6 TOPS | 66.1 | 15.1ms |
| RK3576 (单核) | 6 TOPS | 65.0 | 15.4ms |
| RK3566 | 1 TOPS | 25.5 | 39.2ms |
| RV1126 | ~3 TOPS | 29.2 | 34.2ms |

**我方 A733 实测** (约3 TOPS): `vip_run_network` 27.19ms + `tensor_to_fp` 9.29ms = 36.51ms

**推算区间**: **15-20ms** (置信度中, 远高于此前 8-14ms 的估计)

⚠️ **NPU 标称算力虚高**: RK3588/ARS45/A733 三家实测利用率均仅 **15-20%** (标称 6 TOPS 跑 YOLO 实际约 1.1 TOPS)。**不能用标称 TOPS 推延迟。**

⚠️ **反量化开销是隐藏杀手**: A733 实测 `tensor_to_fp` (INT8→FP32) 占总时间 25% (9.29ms)。若 Art.Galaxy 同样强制 FP32 输出, 实际耗时 = NPU 时间 + 9ms 左右, 直接击穿 16.67ms 预算。

### 3.3 端到端延迟 < 60ms (老板硬指标) —— ⚠️ 10-25 重算, **原来的 42-45ms 结论是错的**


> ✅ **2026-10-25 19:16 老板拍板 Q1 = 口径 A (曝光→出光) + Q17 = 60fps 优先 (兜底 30fps)**
> → **当前承诺基线 = 口径 A @ 60fps = 67.0ms, 超 60ms 预算 7ms**
> → **达标路径 (唯一)**: 纯 NPU 耗时 ≤16.67ms → 框龄 age=1 → 端到端 **50.3ms ✅**; 若 >16.67ms → age=2 → 67.0ms ❌ → **兜底两件一起切** (显示槽位 60→30Hz 且 合成策略 异步→等OD) → **55.7ms @ 25.6fps ✅** (老板已授权, 不再另行请示)
> → ⚠️ **19:26 修正**: 只切帧率不切策略 → 仍 67.0ms ❌ (我 19:16 那版漏了这一层) → 依据 `SW/DISPLAY_MODE.md`
> → **判定动作**: 投板后第一件事测 `M-NPU` (ISS-009 已在原厂问询里); 切换机制由 ISS-044 (sw-lead) 做成可切换配置
> → ⚠️ 口径 A 下的 24.67ms 曝光时间是**不可协商的物理项**, 不接受用改口径的方式"达标"
> **10-25 修正 (软件总工建模后)**: 原表把各环节直接相加, **漏了"框龄 (age)"** —— 即"画在屏幕上的框来自几帧前的画面"。
> 漏了 age 就漏掉了**显示帧率的代价**。重算结果见下, **原 42-45ms 结论作废**。

**记号**: `P` = sensor 帧周期 = 16.67ms (@60fps) · `E` = 曝光 8.3ms · `R` = 读出 8.3ms · `E+R = P`
`T_od` = ISP输出→框可用 (S4 预处理 + S5 NPU + S6 反量化 + S7 decode/NMS) · `age` = ceil(T_od / P)

| 模式 | 显示等 OD? | age | 显示帧率 | 端到端 (口径 A: 曝光开始→出光) | 达标 |
|---|---|---|---|---|---|
| **A** 同帧串行 | 等 | 0 | **~25.6fps** | 16.67+8+22+1+3+5 = **55.7ms** | ✅ 但显示降帧 |
| **B** 异步 60fps | 不等 | 2 | 60fps | (2+1)×16.67+17 = **67.0ms** | ❌ **超 7ms** |
| **B'** 异步 60fps (悲观) | 不等 | 3 | 60fps | 4×16.67+17 = **83.7ms** | ❌❌ 超 24ms |
| **C** 异步 + 快 NPU | 不等 | 1 | 60fps | 2×16.67+17 = **50.3ms** | ✅ 需 T_od ≤16.67ms |

**⚠️ 三个关键结论**:
1. **NPU 延迟是台阶函数, 不是线性** —— 纯 NPU 耗时跨过 16.67ms 边界, age 就从 2 跳到 3, 端到端**直接多一整个帧周期 (16.67ms)**。所以"差 2ms"可能等于"差 17ms"
2. **口径决定生死**: 口径 B (ISP输出→出光) 比口径 A 少 24.67ms; 口径 C 少 24.67ms。→ **模式 B 在口径 C 下是 42.3ms 达标, 口径 A 下是 67ms 不达标** → **Q1 (60ms 口径) 是第一优先级阻塞项, 不只是定义问题**
3. **模式 C 不现实**: T_od ≤16.67ms → 纯 NPU ≤10ms, 比 RK3588 的 15.1ms 还快 34%, yolov5s @640 达不到 → 只能靠换小模型 (yolov5n) 或降输入分辨率

**⚠️ 还没数据的一段**: **S10 光机延迟 = 完全 0 数据**。走鹃Ⅱ 只公开了 480Hz 刷新率, 没有逐帧延迟; 而光机出光**没法用软件打点**, 必须高速摄影或示波器实测。

**分档口径差** (供老板选 Q1 时参考):
| 口径 | 定义 | 与口径 A 差 |
|---|---|---|
| A | 曝光开始 → 光机出光 | 基准 (最严) |
| B | ISP 输出 → 光机出光 | −8.3ms (曝光积分) |
| C | 读出完成 → 光机出光 | −24.67ms (曝光+读出+ISP) |

**待验证的解法 (均需老板/原厂输入)**:
- [ ] **显示帧率要不要 60fps?** 老板锁的是 OD 640×480@60 + 显示 800×600, **没锁显示帧率**。眼镜显示 25-30fps (A7S 项目实测 29.78fps 在用) 完全可以接受 → 若显示帧率放宽, 模式 A 直接达标 (55.7ms)。**这是目前最省事的解法** → 新增 **Q17**
- [ ] 降 NPU 输入尺寸 (640×640 → 512×512) 或换 yolov5n, 把 T_od 压到 16.67ms 以下进模式 C
- [ ] 优化 S6 反量化 (A733 上占 SDK 总耗时 25%): 能否直接拿量化整数输出, 自己反量化只花 0.1-0.3ms → **Q8 追问时必须问清**
- [ ] 光机延迟实测 (高速摄影 / 示波器) —— **需要老板确认能不能借设备**

### 3.4 功耗与续航 ≥ 1h —— ⚠️ 10-25 结构总工重算, **散热是硬约束, 比续航更紧**

**总功耗** (结构总工 10-25 建模, 推算):
| 场景 | 平均功耗 |
|---|---|
| **持续满载** (满帧 OD + 显示 + ISP + 桥) | **0.85-1.52W (中位 1.22W)** |
| 持续满载, **若 ARS45 原生 DSI (无桥)** | 0.75-1.22W |
| **按需触发** (待机 0.15W + 触发时 0.95W, 1s/10s) | **0.23W** |

**🔴 关键: 贴皮肤镜腿的热学上限远低于续航需求**
| 整机功耗 | 皮肤侧温升 | 皮肤侧温度 | 结论 (ISO 13732-1 红线 43°C) |
|---|---|---|---|
| 0.15W | +7.5°C | 42.5°C | ⚠️ 刚好压线 |
| **1.22W (持续满载)** | +61.1°C | **96.1°C** | ❌❌❌ **完全不可接受** |
- 依据: ISO 13732-1:2006 燃烧阈值表 (8h+ 接触 → 塑料/涂层金属等全部 43°C) + CENELEC Guide 29 Table A.1; 镜腿是 8h+ 持续接触
- 设计目标取 **皮肤侧 ≤ 38-40°C** (43°C 是烧伤阈值不是工作温度)
- **⭐ 硬结论: 自然对流条件下, 贴皮肤镜腿可持续承受的功耗上限约 0.15-0.2W**
- **⚠️ 1.22W 持续满载与"眼镜贴皮肤佩戴"热学上不相容, 差 6-8 倍**; **加散热片无效** (只能降功耗)

**续航倒推** (10-25 结构总工修正: 原表漏算充电效率 + 放电截止 DoD, **+23%**):
- 1h 续航所需电池 = 整机功耗 × 1h ÷ 3.7V ÷ (充电效率 ~0.83) ÷ (DoD ~0.9)
- 持续满载 1.22W → **需 ~460mAh+**; 按需触发 0.23W → **~90-130mAh**
- **光机 98mW [官网]** (走鹃Ⅱ 官方, 原表"200-500mW 未知"作废) — 光机**应放镜框**不贴皮肤, 这对散热和佩戴都有利
- ⚠️ **空间反噬**: 电池容量直接决定镜腿厚度 → 340mAh→**7.3mm** / 575mAh→**8.7mm** / 675mAh→**11.2mm (形态否决, 是华为 6.25mm 的 1.8 倍)**

**🔴 结论: "续航 1h" 和 "贴皮肤散热" 是同一个问题的两面, 必须由 Q4 (续航口径) 一起解**
- **按需触发 (0.23W)**: 电池 130mAh, 镜腿 5.5-6.0mm → 空间和散热**同时消失** ✅
- **持续满载 (1.22W)**: 电池 575-675mAh, 镜腿 8.7-11.2mm → 散热超红线 + 形态崩 ❌

### 5.6 OD 分剖率方案 (老板 10-21 19:04 定: 两种规格平级, 优先 640×480)

老板拍板: **640×480 和 800×600 两种规格保留 (平级可选), 优先 640×480** (保 60fps)

| | 640×480 规格 (优先) | 800×600 规格 |
|---|---|---|
| ISP 输出 | 640×480 → 显示上采样 800×600 | 800×600 → 显示原生 |
| NPU 输入 | 640×640 (16.5 GF) | 800×800 (25.8 GF) |
| OD 耗时 | **~15ms** | ~23.5ms |
| 理论上限 fps | **66fps** | 42fps |
| **60fps** | ✅ 卡线 | ❌ 跑不动 |
| 显示画质 | ⚠️ 上采样软 | ✅ 原生 |
| 小目标检测 | 640×480 | 800×600 更好 |

### 5.7 ⏳ FOV / 宽高比问题 (老板 10-21 19:04 提问, **10-24 放宽后重新打开**)

**⚠️ 10-24 老板修正**: sensor 规格 **≥ 1920×1080@60fps 即可, 宽高比不强制 4:3** → 原"横装 4:3 sensor → 全链路 4:3 → 零裁剪"结论**不再自动成立**, 本节重新变成三选一决策。

**背景**: 显示 800×600 (4:3, JBD 走鹃Ⅱ 固定) + OD 640×640 (letterbox) 都是 4:3 系; sensor 宽高比现在自由 → 16:9 sensor 就必须处理宽高比。

**"丢 25%" 的准确含义** (老板质疑后重算, 之前说得不精确):
- **线性宽度丢 25%** (1920→1440): 画面被裁掉左右各 12.5%
- **角度 FOV 丢得少**: 90° HFOV → 2·atan(0.75·tan45°) = **73.7°**, 即 **16.3° / 相对 18%**
- 场景宽度类比: 3m 处场景宽 6m → 裁后 4.5m

**⚠️ 但这是 CHOICE 不是必然** — 三种做法:

| 做法 | FOV | OD 后果 | 适合场景 |
|---|---|---|---|
| **裁剪 (crop)** | 丢 25% 宽 | 最佳精度 (640×480 全有效像素), 但 **左右 25% 场景不检测** | 工业检测 / HUD 叠加 |
| **加黑边 (letterbox)** | 全保留 | 有效像素降到 640×360 (少 36% 纵向), 小目标变差, 但不漏检 | **盲人辅助 (安全优先)** |
| **形变 (stretch)** | 全保留 | 物体几何变形, **检测框会歪** | ❌ 不建议 |

**⚠️ 更大的问题 (待确认)**: 老板 10-20 说 sensor 用"常见手机 sensor 模组", 但**手机镜头 FOV 很窄 (~65-75° 对角)**。智能眼镜需要 **90-120° 对角 FOV** 才有自然视野。
- 手机 sensor (如 IMX415/OV5640) 本身可以配广角镜头, 但:
  - 边缘桶形畸变严重 → ISP 要做 LDC (镜头畸变校正), **占 pipeline 预算**
  - **新 lens + sensor 组合需要原厂做 ISP tuning** (非标组合, 耗时数周)
- **check**: sensor 选型时把"对角 FOV + 镜头是否需畸变校正"当一级指标, 别只看分辨率

#### 5.7.1 10-24 更新: 宽高比方案三选一 (待老板拍板)

| 方案 | sensor 选型 | FOV | OD 有效像素 | 代价 |
|---|---|---|---|---|
| **A. 选 4:3 sensor** (如 2592×1944@60 或 4032×3024) | 豪威 4:3 型号, 横装 | **100% 保留, 零裁剪** | 640×480 全有效 | 4:3 镜更短焦 → 畸变更大, LDC 压力更高; 可选 sensor 池较窄 |
| **B. 16:9 sensor + 裁剪** (1920×1080) | 通用 16:9 手机 sensor | 线性丢 25% 宽 (90°→73.7° HFOV, **丢 16.3°**) | 640×480 全有效, 精度最好 | 左右各 12.5% 场景**不进入显示也不检测** |
| **C. 16:9 sensor + letterbox** (1920×1080) | 通用 16:9 手机 sensor | **全保留** | 降到 640×360 (少 36% 纵向) | 显示区有黑边, 小目标变差; 适合安全优先场景 |
| ~~D. 形变~~ | — | 全保留 | — | ❌ 检测框会歪, 不建议 |

**注**: 方案 A 依然满足老板"≥1920×1080@60"的下限 (2592×1944 = 5MP 4:3 @60)。**"不强制 4:3"不等于"4:3 不好"** —— 4:3 仍能拿到零裁剪 + 更好水平 FOV, 代价是镜头畸变。

**⏳ 选型真正的硬指标 (优先级)**: ① 对角 FOV 100-120° ② 60fps ③ **低畸变镜头 (优先鱼眼/低畸, 减少 LDC 负担)** ④ 原厂有 ISP tuning 支持 ⑤ 豪威优先。

### 10.2 通信拓扑: 星型 (老板 10-25 定, 硬规则)

> **"2.硬件总工、3.软件总工、4.结构总工之间不做直接沟通, 由总工对接我的需求和命令拆分给各个模块"**

| 通道 | 允许? | 技术实现 |
|---|---|---|
| 项目总工 → 三个总工 (下需求/命令) | ✅ | `sessions_spawn(agentId=...)` |
| 三个总工 → 项目总工 (上报/提问) | ✅ | 交接单落盘 `HANDOFF/` + spawn 完成回执自动推回 |
| **三个总工 ↔ 三个总工 (横向)** | ❌ **禁止** | per-agent `tools.deny: ["sessions_send"]` → **配置层硬性禁掉, 发不出去** |
| 三个总工 spawn 别的总工 (借道) | ❌ 禁止 | per-agent `subagents.allowAgents = [自己]` |
| 三个总工 用 exec 横向投递 (`openclaw agent --agent 对方`) | ❌ **禁止 (10-25 压测实测 + 已封)** | **三层拦截**: ① 工具层 `sessions_send` deny ② PATH shim (`tools.exec.pathPrepend`) → exit 126 ③ **CLI 入口包装器** (`~/.npm-global/bin/openclaw`) → 绝对路径调用也 exit 126 (压测实测原来能绕, 消息真投递) |
| 三个总工 **读** 别人的产出区 | ✅ **允许** | 共享项目库 `HW/` `SW/` `MECH/` 互相可读 |

**⚠️ 关键区分 (落地时必须守住)**
- 堵死的是**"对话"**, 不是**"信息"**
- 如果连"读"也堵死 → 硬件画完 PCB 尺寸结构总工看不到, 结构画完外形硬件总工看不到, 三个总工各写各的, 项目总工变成人肉路由器, 传话必然失真
- 所以: **横向信息流走文件 (共享产出区), 不走会话**。需要对方配合时写**接口请求**交接单给项目总工, 由项目总工转达或组织三方评审

**代价与配套 (项目总工必须承担的)**:
1. **接口必须提前书面固化** → 新增 `INTERFACES.md` (硬件↔软件↔结构 接口契约表)。不能靠对话拉齐
2. **同一份需求文档同时下发三方** → `REQ/REQUIREMENTS.md`, 避免口头转述失真
3. **跨模块评审只能由项目总工组织** → 收集 → 转交 → 收意见 → 裁决 → 落盘 `INTERFACES.md`
4. **收口时必须做跨模块接口一致性检查** → 否则会出现"三个总工各写各的, 没人发现接口对不上"

### 10.6 共享状态源 STATE.yaml (老板 10-25 指示) —— ✅ 已落地

> 老板原话: "总工和3个子模块总工之前可以通过共享 **STATE.yaml** 文件作为唯一状态源, 避免跨专业 Agent 的无效沟通冲突"

**为什么需要**: 星型拓扑的副作用是"A 想知道 B 的进度只能靠问" → 问了就是一次跨 agent 往返, 经常变成"我催你→你回我→我转达→失真"。**STATE.yaml 把"问"变成"读"。**

**结构 (分片所有权 → 无并发冲突 → 合并器唯一写)**:
```
STATE.yaml                      ← 合并产物 (机器可读), 全员只读
state/fragments/pm.yaml         ← 项目总工独占写
state/fragments/hw.yaml         ← 硬件总工独占写
state/fragments/sw.yaml         ← 软件总工独占写
state/fragments/mech.yaml       ← 结构总工独占写
state/merge.py                  ← 合并器: 纯函数 / 无锁 / 原子写 (tmp+rename)
state/test_merge.py             ← 合并器自测
```

**三个机制 (直接对应老板说的"避免无效沟通冲突")**:
| 机制 | 解决什么 | 怎么用 |
|---|---|---|
| **needs_from × answers 按 key 配对** | "我催你→你回我"的往返 | 需求方写 `needs_from: {key, to, item}`; 回答方写 `answers: {key, to, value, ref}` → 合并器自动标 `answered`。⚠️ **只有被问的那个 agent 的回答才能闭合需求** (别人代答记入 `foreign_answers`) |
| **interface_claims 自动查冲突** | "两个人理解不一样但没人发现" | 同一 `key` 给了不同规范值 → 自动进 `conflicts`。`value` 必须短 (如 `50x12mm`), 说明写 `note`; 写成散文 → 标 `lint` 且不参与比较 (防假冲突) |
| **`--for <agentId>` 切片** | "我该先干哪个" | 一屏看清: 别人在等我什么 / 我欠谁什么 / 当前冲突 / 高危阻塞 |

**`STATE.yaml` vs `PROJECT_TRACKER.md` 的分工 (避免两个真源)**:
| | 放什么 | 谁写 |
|---|---|---|
| `STATE.yaml` | **当前状态快照** (机器可读): 做到哪 / 卡在哪 / 在等谁 / 接口值 / 冲突 | 合并器生成, **人不手改** |
| `PROJECT_TRACKER.md` | **决策与理由真源** (人读): 锁死变量 / 决策记录 / 证据链 / 展开分析 | **只有项目总工** |

关系单向: STATE 每项带 `ref` 指向 tracker 章节或产出文件。**状态变了 → 两边一起改。**

**当前快照 (10-25 01:05)**: 产出 11 · 阻塞 15 (高危 13) · 未闭合需求 18 · 冲突 0 · 健康度 red

> 窗口期纪律: 周五 10:00-12:00 **不派临时活**, 避免同一 agent 两个写会话互相覆盖分片。

#### (4) 出了问题怎么确认 —— 四道门 + 一条铁律

**发现 (靠漂移, 不靠自觉)**
- 每天 09:00 自动跑 `daily_check.py`, 与上一次快照逐项比: 齐备率掉了 / 内部未闭合多了 / 问题单多了 / 逾期多了 → **★漂移报警**
- 四个子 agent 交卷时必须**自己跑自证** (merge rc + gate 数字), 自证不过 = 不计交卷

**定责 (问题单有唯一 owner)**
- `issue_log.yaml` 每条: id / severity / owner / reporter / due / status / fix_ref / verify_by
- **外部依赖 (等老板/原厂/JBD) 单独标 external** → 不算总工失职, 但必须有 verify_by 盯着, 否则就是"没人追"

**修复**
- 状态机: `open → fixing → fixed → verified → closed` (不许跳级)
- **★铁律: 验证分离 —— verify_by ≠ owner**。自己修自己验 = 没验 (已负向测试: 注入自验后 issue_check rc=1 抓出)

**确认 (三条硬判据)**
1. `fix_ref` 必填 (没修就关 = 不许)
2. `verify_result == pass` 且 `verify_by != owner`
3. **双向覆盖**: STATE 里每个 high/blocker 阻塞都必须有 issue 登记; issue 引用的 `source_blocker` 必须真实存在 (防幻觉引用)

**升级**
- `due` 逾期未闭环 → 自动升级到我, 并进每日报告
- 我 24h 内决定: 转派 / 拆解 / 降级 / 升级给老板

#### (5) 怎么有序开展直到完美结束 —— 5 道阶段门

| 门 | 名称 | 准出判据 | 当前 |
|---|---|---|---|
| **G0** | 纸面冻结 | 4 个老板拍板项已答 + 3 条口径 issue 闭环 | ⏸️ 缺 7 项 |
| **G1** | 原理图/PCB 定稿 | 8 条原厂类 issue 闭环 (pitch/电源域/显示 TX/启动存储) | ⏳ 缺 8 项 |
| **G2** | 结构样机装配 | 4 条 JBD/打印件 issue 闭环 + **3 项实测** (打印件尺寸/干涉/重量) | ⏳ 缺 7 项 |
| **G3** | 上电联调+硬指标实测 | 2 条 issue 闭环 + **7 项实测** (NPU/端到端/皮肤/功耗/续航/充电/光机) | ⏳ 缺 9 项 |
