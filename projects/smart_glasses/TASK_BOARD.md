## §7 ★ 2026-11-01 断电恢复: 两个"机制自己骗自己"的真缺陷 (本轮修了)

> ★**这一节记的是"机制层面的病"** —— 不是某条 issue, 是**老板 10-29 亲自定的工作方式**里的两个洞。两条都是"看起来在工作, 实际没工作"。

### ★★缺陷 1: GitHub 发布闸门把**凭据明文写进了要公开的脚本里** (10-30 遗留)

- **现象**: `state/publish_github.sh` 里写着 `EXTRA_LITERALS = ["<openid 前半段>" + "<openid 后半段>"]` —— **拆拼**形式, 骗过了"自己扫自己"那关; 但**两段明文都在文件里**, 而这个脚本**本身会被 rsync 进公开仓库** ⇒ grep 一下就能拼回完整凭据 ⇒ **等于把凭据发到公开仓库**。
- **修法**: **脚本里一个敏感串明文都不写**, 全部从**本地不入库的真值源**现读:
  - `~/.openclaw/openclaw.json` (token/apikey/secret) · `~/.openclaw/cron/jobs.json` (推送目标) · `~/.../TOOLS.md` `MEMORY.md` (设备口令)
- **★附带修的**: 设备口令 `radxa` 原来用 `radxa` 匹配 ⇒ **误伤 6 个正常文件** (`~/Downloads/radxa/...` 路径) ⇒ 改成**上下文匹配** (`sshpass -p X` / `密码: X` / `password=X`) 且**规则由真值动态生成** ⇒ 脚本源码里也不出现口令字面量。
- **自测**: 真实发布树 **0 命中** + 故意造 4 类泄漏文件 **全部被抓到** (含实盘真实格式 `**SSH 密码**: \`radxa\``) ⇒ 命令: 跑 `state/publish_github.sh` 第 4 步。

### ★★缺陷 2: token 守护的"最可靠兜底"在**骗自己** (老板定的第②条判据)

- **现象**: `state/token_watch.py` 用 **文件 mtime** 算"距上次 GitHub 推送多久"; 而 `.last_github_push` 是**内容为时间戳**的记录文件 ⇒ **任何一次重写它 (哪怕只是把旧时间戳写回去) 都会刷新 mtime** ⇒ 判据报"刚推过", 实际可能 2 天没推。
- **血证**: 11-01 20:52 我把内容改回真实推送时间 (10-30 00:21) 后, token_watch 报 **"距上次 GitHub 推送 4.5 分钟"** —— 内容明明是 2 天前, 它说 4.5 分钟。
- **修法**: **读文件内容里的 ISO 时间戳**算间隔; 内容缺失/解析失败才回退 mtime。修完如实报 **4115 分钟前没推** ⇒ rc=3 正确触发推送。
- ★**为什么这条最要紧**: 老板 10-29 说"距上次推送超 45 分钟"是**最可靠的兜底** (因为限额数值本身未公开) ⇒ **它骗自己 = 兜底失效 = 断电时什么都留不下来**。
