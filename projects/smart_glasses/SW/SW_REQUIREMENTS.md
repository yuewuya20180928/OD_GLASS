## 1. 软件模块拆解总览

顶层需求 → 8 个软件模块。模块边界按"**谁拥有这个文件/接口**"划, 不按"哪个流程"划。

```
                    ┌──────────────────────────────────────────────┐
  M1 BSP/驱动 ───▶ │  M2 ISP 调参                                 │
   (内核/设备树/    │   (AE/AWB/LDC/缩放/EIS 开关/输出分辨率)     │
    sensor/ISP/    └───────────────┬──────────────────────────────┘
    NPU/显示/PM)                   │ 800×600 显示帧 + 640×480 OD 帧
                    ┌───────────────▼──────────────┐
                    │  M6 显示合成 (画框 + 叠加)     │──▶ M1 显示 TX 驱动
                    └───────────────┬──────────────┘
                    ┌───────────────▼──────────────┐
   M3 NPU runtime  │  M5 OD 应用 (main + worker)    │
   (Art.Galaxy) ◀──┤   pre / infer / decode / NMS   │
                    └───────────────┬──────────────┘
                    ┌───────────────▼──────────────┐
                    │  M4 模型转换 (ONNX→Art.Galaxy) │
                    └──────────────────────────────┘
   M7 电源管理 (贯穿)          M8 调试升级通道 (贯穿)
```

| ID | 模块 | 一句话职责 | 主要产出物 | 证据状态 |
|---|---|---|---|---|
| M1 | BSP / 驱动 | 让 ARS45 能起来并把 sensor→NPU→显示 这条硬件链路跑通 | 内核版本 + 设备树 + 驱动补丁 | 🟡 无 datasheet, 全部待定 |
| M2 | ISP 调参 | 出图质量 (AE/AWB/LDC/EIS) + 出图速度 (吞吐/延迟) | ISP 参数集 + 吞吐实测 | 🟡 ISP 吞吐口径本身自相矛盾 (见 §6) |
| M3 | NPU runtime | 把 Art.Galaxy 的 SDK 跑通, 并把**纯 NPU 耗时**和**SDK 总耗时**分开测出来 | runtime 封装 + 基准程序 | 🔴 **最大未知数** |
| M4 | 模型转换 | yolov5s 80 类 ONNX → Art.Galaxy 可跑格式 | 模型 + 转换记录 + 算子覆盖表 | 🟡 工具链成熟度未知 |
| M5 | OD 应用 | 采集→推理→解码→NMS→画框 的实时流水线 | C++ 进程 + 打点 | 🟢 线程模型有 A7S 验证过的成熟方案 |
| M6 | 显示合成 | 把框叠加进 800×600 帧, 交给显示 TX | 合成层 + DisplaySink 抽象 | 🟡 输出接口未定 (Q16) |
| M7 | 电源管理 | 整机功耗可控, 续航 ≥1h | 功耗打点 + DVFS/省电策略 | 🟡 整机电耗全是推算 |
| M8 | 调试升级通道 | 无网络情况下能装模型/改参数/抓日志 | ADB + OTA 方案 + 日志系统 | 🟡 Q3 未答 |

**关键依赖链**: M3 → M4 → M5 是串行的 (没模型就没推理, 没推理就没 OD 数据)。
M1 → M2 → M6 也是串行的。
→ **投板后第一个 30 天只够验证 M1/M3/M5 三条线**, M2/M6/M7 靠纸面设计。

## 2. M1 — BSP / 内核 / 驱动

### 2.1 职责
- Linux 内核版本选型与裁剪 (ARS45 vendor kernel, 待 datasheet)
- 设备树 (DT): sensor / ISP / NPU / DSI(或 DP) / PMIC / 电池 / Type-C 节点
- 驱动适配: MIPI-CSI sensor 驱动, ISP 驱动与参数下发, NPU 驱动 (devfreq/dvfs), 显示 TX 驱动
- 电源管理框架接入 (regulator / OPP / 电源域)
- 系统启动: bootloader → kernel → rootfs, 开机自启 OD 进程 (systemd service)

### 3.3 ⚠️ 关键矛盾 (必须让项目总工 close)

`PROJECT_TRACKER.md` §3.1 用"4K@30fps 单路 ≈ 250 MP/s"反推 ISP 吞吐, 得出**全幅 2688×1520@60** 关 EIS 占 49.8% — *旧链路命名 "1080p@60" = 旧链路, 现锁定链路 = 全幅 2688×1520@60 (裸 "1080p" 对 OV04C10 等于 ROI 读出, 见 §3.4.3)*。
但同一份材料说"7 路 4K@30" —— 7 路 × 4K30 = 7 × 124 MP/s = **870 MP/s**, 与 250 MP/s 差 3.5 倍。

→ **这个吞吐口径本身自相矛盾, 用它算的 49.8% 不可信。** 项目总工 MEMORY.md 已记录此问题但未 close。

**软件侧影响**: ISP 段延迟预算是按"原厂口径 Sensor 输出→显示屏出图 <10ms"给的 (官方口径), 这个数**不依赖**上面那个 MP/s 推算, 所以延迟预算表不依赖这个矛盾。但**多路并发能力**依赖它 —— 如果后面要加第二路 MIPI (双路 MIPI 是原厂宣传点), 必须先 close。

**我的处理**: 延迟预算里 ISP 段用官方口径 (E2), 不用 MP/s 推算; 吞吐问题单列为 Q10 追问项。

### 3.4 ISP 缩放模式硬约束 (ISS-056)

> **归属**: sw-lead · 2026-10-26 · **来源**: ISS-053 自查发现 (§2.4 表3 + R-GEO-1) → 升级为正式需求。

#### 3.4.1 硬约束原文 (不可改写)

> **ISP 缩放路径必须为整幅 scale (full-frame scale), 禁止 ROI 裁剪 (crop+scale)、禁止 sensor ROI 读出模式、禁止为凑 4:3 而做的 aspect crop; ISP 输入必须是 sensor 全幅阵列。**

拆成 4 条禁止 + 1 条强制:

| # | 约束 | 违反后果 (量化) |
|---|---|---|
| **C1** | 缩放路径 = **整幅 scale** (取 sensor 全幅阵列 → 缩放) | OV04C10: 对角 FOV 120.00° → **85.61°**, 垂直半视场 29.53° → **20.98°**, 立体角只剩 **52.30%** (损失 47.70%) `[推算·本文推导]` |
| **C2** | **禁止 sensor ROI 读出模式** (OV04C10 的 1920×1080 / AR0234CS 的裁高 1080p) | OV04C10 同 C1; AR0234CS 裁高 → 对角 116.75°, 立体角 90.30%, 俯角 28° 时余量仅 +0.62° `[推算·本文推导]` |
| **C3** | **禁止为凑 4:3 而做的 aspect crop** (把 16:9 / 16:10 裁成 4:3) | OV04C10 全幅裁成 4:3 (宽 2688→2026.67) → 线性丢 24.60% 宽, 水平半视场 52.23° → **39.38°** (HFOV 104.45° → 78.76°, **丢 25.70°**) `[推算·本文推导]` |
| **C4** | **禁止 ROI 裁剪 (crop+scale)** (ISP 内部先 crop 再 scale) | = C1 (等价) |
| **C5** | **ISP 输入必须是 sensor 全幅阵列** (OV04C10 2688×1520@60 / AR0234CS 1920×1200@60) | C1~C4 的实现前提 |

**为什么是硬约束 (不是建议)**: 老板 10-25 19:33/19:42 拍板 "sensor 输出不裁剪, 后级只缩放" + "鱼眼 (等距) + 对角 120°"; ROI 路线同时违反这两条, 而且裁掉的正是 **角落 −39.5% 桶形畸变区 = 目标刚进入画面处 = 检测价值最高处** `[官方·HW/LENS_SELECTION.md §4]`; 叠加俯角 25° (OV04C10) / ≤28° (AR0234CS) 的结构约束, ROI 路线下 **正前方余量 −4.02° = 直接掉出画面** `[推算·本文推导]`。

### 4.3 ⚠️⚠️ 硬性要求: 纯 NPU 耗时 vs SDK 总耗时必须分开报

**这是 A7S (A733) 实测得出的铁律, 直接决定本项目会不会踩同一个坑。**

A733 实测 (我方板端, E1):
| 口径 | 数值 | 说明 |
|---|---|---|
| `vip_run_network` (纯 NPU) | **27.19 ms** | NPU 硬件真正在算的时间 |
| `awnn_run` total (SDK 总) | **36.51 ms** | SDK 一次调用返回的总时间 |
| 差值 `tensor_to_fp` | **9.29 ms (占总 25%)** | INT8→FP32 **软件反量化**, 不是 NPU 在算 |

**为什么这在本项目是生死线**:
- 640×640 yolov5s @60fps 的帧周期只有 **16.67ms**。
- 若 ARS45 的 Art.Galaxy runtime 像 A733 一样强制 FP32 输出, 且纯 NPU 耗时是 15ms, 则 SDK 总 = 15 + ~9 = **24ms** → **单帧就超一帧周期**, 60fps 配置直接不成立。
- 横向对比也必须统一口径: RK3588 model_zoo 的 15.1ms 是**哪个口径**? 如果是纯 NPU 而我们是 SDK 总, 直接对比得出的结论是错的。

**具体动作 (M3-R2 的落地方式)**:
```c
// 板端计时点设计 —— 三段式, 不要合成一个数
t0 = now();                       // 调用前
npu_sdk_run(net);                 // SDK 总入口
t1 = now();                       // SDK 返回
npu_pure_run(net);                // 或 SDK 提供的纯 NPU 计时接口
t2 = now();
report(npu_sdk_total_ms = t1-t0); // 口径 A
report(npu_pure_ms      = t2-t1); // 口径 B
report(quant_overhead_ms= t2-t0); // 反量化 + 输出拷贝
```
> 若 Art.Galaxy 不暴露纯 NPU 计时, 则退而求其次: **同一模型在 SDK 内自带的 profiling 日志里找硬件段**, 或**用"INT8 直通 vs FP32 输出"两条路径的耗时差反推**。两种办法都不够干净, 所以 Q9 里要专门问。

**Q9 追加提问 (给项目总工, 加进第二轮邮件)**:
> ① yolov5s INT8 @640×640 的实测耗时, **是纯 NPU 耗时还是 SDK 总耗时**?
> ② 输出 tensor 能否直接取 INT8 量化整数 (不经过 FP32 中间态)? 若可以, 反量化在应用侧做需多久?
> ③ runtime 是否提供分阶段 profiling (NPU 硬件段 / DMA / 后处理)?
> ④ 连续跑时 NPU 有没有降频? 首个推理是否比稳态快 (缓存预热)?

### 4.4 证据状态
🔴 **本项目最大的未知数, 且已经确认"网上查不到"**:
- 原厂**从没公开跑过 YOLO**。讯飞 2026-05-28 的翻译眼镜用的是 ARS45, 但跑的是语音识别/翻译/唇语识别/多模态降噪, **不是 YOLO**。

## 6. M5 — OD 应用 (实时流水线)

### 6.1 线程模型 (A7S 架构 A, 直接复用)

```
main thread (采集 + 合成 + 显示提交)          worker thread (OD)
===================================          ========================
while:                                      while:
  DQBUF / get ISP frame                       wait q_frame (block)
  letterbox → NPU 输入 tensor 准备              pre_process (letterbox/量化)
  push q_frame (共享 buffer, 不 copy)           npu_run  (纯 NPU + SDK)
  try_pop_latest(q_result) → last_boxes        get_output_buffers
  draw last_boxes on current 显示帧              yolov5_decode_all
  submit to DisplaySink                        yolov5_nms
  QBUF / release frame                          push q_result (max=1)
```

**设计约束 (来自 A7S 实测教训, 直接写成硬性规则)**:
| 规则 | 来源 |
|---|---|
| **OD 慢时不能反向拖累采集** —— OD 必须在独立线程, main 绝不等 OD | A7S 实测: 单线程 OD pipeline 35-44ms/帧 → fps 从 29.66 掉到 19.83; 拆线程后 **19.83 → 29.78** |
| **禁止 blocking acquire 的 ring buffer** | A7S 实测: BgrRing (3 slot, mutex+cv) 让 main 阻塞 12-56ms 等 OD release, fps 从 29.66 **退步到 24.5**。规则: OD 慢 ≥5% 时不用 blocking acquire |
| **copy 开销 0.5ms 可接受, backpressure 不可接受** | A7S: `bgr.clone()` 0.5ms 换 main 不等 OD, 是最优解 |
| **框龄 (age) 必须显式跟踪并打点** | A7S 教训: 框永远晚 1 帧 (33ms), 且 OD 慢 17% 时新帧覆盖旧框, 但当时**没有指标**能看出框到底多旧 → 本项目必须打点 |
| **不做 OD_SKIP (隔帧检测)** | 老板 2026-10-11 明确否决: "为了保证检测的效果是不可能隔帧检测的" |

```
        │  - 输出: 画好的 800×600 帧          │

                        │ 纯虚函数接口 (不依赖任何 TX 细节)
        ┌───────────────▼──────────────────┐

   └──────────────────┘  └────────────────────┘
```

**这样做的三个理由**:
1. **合成层 90% 的代码与 TX 类型无关** —— letterbox 逆映射、画框、坐标裁剪、标签渲染, 这些现在就能写完并用 PC 端假数据单元测试。
2. **只有 buffer 分配策略依赖 TX** —— DSI TX 的 framebuffer 可能要求物理连续 / 特定对齐; DP 的可能不要求。→ 把 buffer 分配下沉到 Sink 实现里, 合成层只管交出"逻辑帧"。
3. **像素格式做成可配** —— 桥芯片厂商的参考设计会指定输入格式 (RGB888 / RGB565 / YCbCr422), DSI TX 可能要 NV12。合成层的输出格式参数化, 换 TX 时只改配置不改代码。

**不能等 Q16 的部分 (现在就写)**:
- DetBox 结构、画框、标签
- 坐标映射 (letterbox 逆变换 + 显示帧裁剪)
- 框龄追踪 (frame_id 传递)
- DisplaySink 接口定义 + 一个 PC 端 mock 实现 (用于单元测试)

**必须等 Q16 的部分**:
- 真正的 TX 驱动调用
- framebuffer 的物理内存分配方式
- 桥芯片的延迟与功耗 (要填回 §9 预算表)
- 像素格式最终取值

### 10.2 建模: 端到端延迟到底怎么算 (这一步决定结论对不对)

**记号**: `P` = sensor 帧周期 = 16.67ms (@60fps) · `E` = 曝光积分 8.3ms · `R` = 读出 8.3ms · `E+R = P`
`T_od` = S4+S5+S6+S7 (从 ISP 输出到框可用) · `age` = 框龄 (框来自几帧前的画面)

**时序事实** (sensor 与 OD 与显示三者并行):
```
t=0            曝光 N 开始
t=E+R=16.67    读出完成 → ISP 开始
t=24.67        ISP 输出 N 就绪 ──┬─→ OD 开始, 框在 t=24.67+T_od 就绪
                               │
                               └─→ 显示帧 N 可合成 → 画框 → TX → 光机
                                    (若要等框, 这里就得等)
显示帧 M 的合成时刻 = 16.67M + 16.67 + S3
框 N 能落到显示帧 M ⟺ 16.67M + 16.67 + S3 ≥ 16.67N + 16.67 + S3 + T_od
                      ⟺ M - N ≥ T_od / 16.67  ⟹  age = ceil(T_od / P)
```

**三种流水线模式** (这是延迟设计的真正选择, PROJECT_TRACKER §3.3 把它简化掉了):

| 模式 | 显示是否等 OD | 框龄 | 显示帧率 | 端到端 (口径 A: 曝光开始→出光) |
|---|---|---|---|---|
| **模式 A** 同帧串行 | **等** | age=0 (框就是这一帧的) | 1/(S3+T_od+S8+S9+S10) ≈ **25.6fps** | `P + S3 + T_od + S8 + S9 + S10` = 16.67+8+22+1+3+5 = **55.7ms** ✅ |
| **模式 B** 异步 (显示 60fps) | 不等 | age=ceil(T_od/P) = **2** | **60fps** | `(age+1)×P + S3 + S8 + S9 + S10` = 50.01+17 = **67.0ms** ❌ |
| **模式 C** 异步 + 快 NPU | 不等 | age=**1** (需 T_od ≤ 16.67) | **60fps** | 2×16.67+17 = **50.3ms** ✅ |

**⚠️ 关键**: 模式 B 里, NPU 变慢**不直接增加**端到端时间, 而是**把 age 从 2 推到 3**, 一次跨一整个帧周期 (16.67ms)。这就是 NPU 延迟的"台阶效应"。

### 10.3 ⚠️ 与 PROJECT_TRACKER §3.3 的差异 (必须让项目总工知道)

`PROJECT_TRACKER.md` §3.3 的合计表是这么加的:
> sensor 曝光+读出 16 + ISP+缩放+显示出图 <10 + OD 推理 14 + decode+NMS+画框 2~5 = **42-45ms, <60ms 达标**

它假设了 **ISP 与 OD 串行相加** (即模式 A), 得出 42-45ms 达标。但这个算法:
1. **没算框龄** —— 模式 A 的代价不是 0, 而是**显示帧率掉到 ~25.6fps**。42-45ms 这个数字只有在"显示降到 25fps"的前提下才成立, 而 §3.3 没提这个代价。
2. **光机延迟按 0 计** (§3.3 明说 "光机按 0 待实测") —— 而 S10 是 0 数据项。
3. **用了老板指定的 14ms NPU 值** —— 但 §3.2 自己说推算区间是 15-20ms, 14ms 比推算下限还乐观。

→ **我的结论: §3.3 的 "42-45ms 达标" 是在"显示降到 25fps + 光机延迟 0 + NPU 取 14ms"三个乐观假设同时成立时才成立的。这三个假设没有一个有实测支撑。**
→ **但这不是否定 §3.3, 是给它补上"显示帧率"和"光机延迟"两个缺口, 让老板知道达标是有条件的。**

### 10.4 三种口径 × 三种模式的完整矩阵 (推算)

**乐观场景**: NPU 纯硬件 16ms + INT8 输出直通 (S6=2ms) → T_od = 1+16+2+3 = **22ms** → age=2
**悲观场景**: NPU 纯硬件 20ms + 强制 FP32 输出 (S6=9.3ms) + decode 5ms → T_od = 1+20+9.3+5 = **35.3ms** → age=**3**

| 口径 | 模式 A (≈25.6fps, age=0) | 模式 B (60fps, 乐观 age=2) | 模式 B (60fps, 悲观 age=3) | 模式 C (60fps, age=1) |
|---|---|---|---|---|
| **A. 曝光开始 → 光机出光** | 乐观 **55.7** ✅ / 悲观 **69.0** ❌ | **67.0** ❌ | **83.7** ❌❌ | **50.3** ✅ |
| **B. 曝光结束 → 光机出光** | 乐观 **47.4** ✅ / 悲观 **60.7** ❌ | **58.7** ⚠️ 余量1.3 | **75.4** ❌ | **42.0** ✅ |
| **C. 框对应帧的 ISP 输出 → 光机出光** | 乐观 **31.0** ✅ / 悲观 **44.3** ✅ | **42.3** ✅ | **59.0** ⚠️ 余量1.0 | **25.7** ✅ |

> **口径 C 的定义说明**: 这里取的是"**框是从哪一帧的 ISP 输出算出来的** → 光机出光"。
> 另一种读法是"**被显示的那一帧自己的 ISP 输出 → 光机出光**", 那个值 = S8+S9+S10 = **9ms**, 与 OD 完全无关 —— 它只测显示链路, 对验收整链路没有意义。**这两个数不要混。**
> 口径 B = 口径 A − 8.3 (曝光积分); 口径 C = 口径 A − 24.67 (曝光+读出+ISP)。

> 模式 C 需要 T_od ≤ 16.67ms → **纯 NPU ≤ 10ms** (扣掉 S4+S6+S7 = 6ms)。比 RK3588 的 15.1ms 还快 34%, yolov5s @640 不太可能达到 → **模式 C 只能靠换小模型 / 降输入分辨率实现**。

> ⚠️ **上表全是推算 (E3/E5 级输入), 没有任何一格是实测。投板前不能拿这张表说"达标"。**
> ⚠️ **S10 (光机延迟) 全部按 5ms 占位, 是 0 数据。** 若实际是 8ms, 上表每一格再加 3ms。
> ⚠️ **模式 A 的"显示 25.6fps"是硬代价**, 必须让老板知道这个取舍 (与 Q2 联动)。

### 10.5 ⚠️ 三个关键结论

**结论 1: 口径决定生死 (Q1 是软件侧第一优先级)**
同一套硬件, "曝光→出光" 口径比 "ISP 输出→出光" 口径多 **24.67ms** (曝光 8.3 + 读出 8.3 + ISP 8.0)。
在这个严口径下: 模式 A 乐观 55.7ms ✅ 勉强达标; 模式 B 60fps 方案 **67ms ❌ 超 7ms**。
→ **Q1 不答, 我就没法给老板一个"达标/不达标"的结论。** 这是软件侧最值钱的一个待确认项。

**结论 2: 框龄 (age) 是 PROJECT_TRACKER §3.3 漏掉的一整项**
- age 的取值完全由 T_od 落在哪个 16.67ms 区间决定, 是**台阶函数**, 不是线性。
- age 每涨 1 档, 端到端涨一整个帧周期 16.67ms。
- **age=1 需要纯 NPU ≤ 10ms** —— 这比 RK3588 同类模型还快 34%, yolov5s @640 基本做不到。
- **age=2 是现实预期** (T_od 16.67~33.3ms)。若 FP32 输出被强制 (T_od=35.3ms) → **age=3**, 端到端直接冲到 83.7ms。
- → **"INT8 输出能否直通"这一件事, 值 16.67ms 端到端预算。**

**结论 3: NPU 延迟买的是"台阶", 不是"线性"**
| 纯 NPU (S5) | S6 | T_od | age | 端到端 (口径A, 模式B) |
|---|---|---|---|---|
| 10ms | 2 (INT8 直通) | 16ms | **1** | **50.3ms** ✅ |
| 11ms | 2 | 17ms | 2 | 67.0ms ❌ ← **只差 1ms 就跨台阶** |
| 16ms | 2 | 22ms | 2 | 67.0ms ❌ |
| 16ms | 9.3 (FP32) | 29.3ms | 2 | 67.0ms ❌ |
| 20ms | 9.3 | 35.3ms | **3** | **83.7ms** ❌❌ |
→ **把纯 NPU 从 16ms 压到 10ms, 端到端省 16.7ms (整整一个帧周期)。** 这是全项目杠杆最大的一个优化点。
→ 收敛手段优先级: ① **确认 INT8 输出直通** (S6 从 9.3 → 0.3, 顺带避免 age 跨台阶) ② yolov5s → yolov5n ③ NPU 输入 640 → 512 ④ 降 OD 帧率 (需 Q2 拍板) ⑤ 模式 A (显示等 OD, 25.6fps) 作为兜底方案

### 10.6 预算表里证据最弱的 5 段 (按弱到强排序)

| 排名 | 段 | 为什么弱 | 缺什么 |
|---|---|---|---|
| 1 | **S10 光机延迟** | 走鹃Ⅱ 页面只有 480Hz 刷新率, **没有任何逐帧延迟数据**。这是唯一"完全 0 数据"的段 | 找 JBD 要 latency 数值 / 高速摄影法实测 |
| 2 | **S5 NPU 纯硬件耗时** | 原厂**从没跑过 YOLO**, 公开渠道查不到; 只有 Rockchip 同段位横评可类比 | 投板实测 (Q8) |
| 3 | **S6 SDK 后处理开销** | A733 实测的 9.29ms 是**别的芯片的别的 SDK**。Art.Galaxy 是否强制 FP32 输出 = 完全未知 | Q9 追加提问 |
| 4 | **S9 显示 TX 延迟** | "3ms" 是媒体转述的方案级宣传语, 且**若走桥接芯片则整个作废** | Q14 + 桥芯片 datasheet |

## 11. 性能打点方案 (A7S 最值钱的资产, 直接复用)

### 11.1 设计原则
1. **每个阶段边界一个打点**, 用 `clock_gettime(CLOCK_MONOTONIC)` (不用 `CLOCK_REALTIME`)。
2. **纯 NPU 与 SDK 总耗时是两个独立打点**, 不合并 (见 §4.3)。
3. **三个 fps 分开报**: 采集 fps / OD fps / 显示 fps。A7S 教训: 只报总 fps 看不出 OD-bound。
4. **每段输出 min/avg/max + 采样帧数**, 不允许只报 avg。A7S 就是靠分段才定位到"OD 35-44ms 是主因"。
5. **框龄 (age) 单独打点** —— A7S 缺这个指标, 导致"框永远晚 1 帧"这件事没人知道。

### 11.2 打点字段表 (板端 CSV 格式)

| 字段 | 含义 | 打点位置 |
|---|---|---|
| `frame_id` | 采集帧序号 | 采集循环 |
| `t_capture` | 帧进入用户态的时间戳 | DQBUF / ISP 输出回调 |
| `t_isp_out` | ISP 输出就绪 | ISP 输出回调 |
| `t_pre_in` | OD 预处理开始 | worker 线程 |
| `t_npu_call` | NPU 调用前 | worker 线程 |
| `t_npu_pure_end` | 纯 NPU 硬件段结束 | SDK 提供的分段计时 (若无 → 标记不可用) |
| `t_npu_sdk_end` | SDK 调用返回 | worker 线程 |

### 12.2 结论
- **静态 + 峰值 ≈ 200-215MB, 占 512MB 的 ~42%** (悲观合计向上取整 ~216MB ÷ 512MB = 42.2%) → **内存不是本项目的瓶颈**。
- 余量 ~296MB (512MB − 悲观合计向上取整 ~216MB), 足够吸收: 双路 MIPI (第二路 sensor)、CMA 预留、**若将来显示升到 1080p (未锁定)** 需追加显示 framebuffer (~33MB)、NPU SDK workspace 膨胀。
- **PROJECT_TRACKER 风险 R7 "512MB 内存规划" 建议从 🟡 中降级到 🟢 低**, 但保留两个必须确认项 (见 §12.4)。

### 12.3 buffer 数量推导 (公式: buffer 数 = fps × 可容忍延迟)

| buffer | 深度 | 推导 | 依据 |
|---|---|---|---|
| ISP 内部 | 4 | 1 在处理 + 1 在填 + 2 抗抖动 | `推算` |
| CSI capture queue | 4 | 同上; 若 ISP 与 CSI 共享 buffer 则可省 | `推算` |
| OD 帧队列 (q_frame) | **2** | A7S 实测值: `push_drop_oldest`, OD 永远算最新帧 | `实测` (A7S) |
| OD 结果队列 (q_result) | **1** | `try_pop_latest`, main 只用最新结果 | `实测` (A7S) |
| 显示 framebuffer | 3-4 | 双缓冲防撕裂 + 1 抗抖动 | `推算` |
| NPU 输入 tensor | 2 | 一份在跑, 一份在填 | `推算` |
| NPU 输出 tensor | 2 | 一份在跑, 一份在取 | `推算` |

> ⚠️ **深度不是越大越好**: A7S 实测 ring buffer 深度 3 + blocking acquire → main 阻塞 12-56ms, fps 从 29.66 退到 24.5。**backpressure 会反向拖累采集, 这是本项目最贵的教训之一。**

### 12.4 ⚠️ 内存侧两个必须确认项 (目前没数据)

1. **NPU SDK 内部 workspace 大小** —— 未知, 我按 20MB 猜。这是最容易出意外的一项: 如果 SDK 内部要开一个大 arena + CMA 连续块, 可能吃掉 50-100MB。
2. **CMA (contiguous memory) 预留策略** —— NPU 和 ISP 都需要大块连续物理内存。预留多少、策略是什么, 没有 datasheet 不知道。若 CMA 预留不足, 表现为**第一次跑大模型时 OOM**, 而且是运行时才炸, 不是启动时。
   → **动作**: 拿到 kernel 配置后第一件事看 `cma=` 参数和 `/proc/meminfo` 的 CmaTotal/CmaFree, 并在 M1-R7 里加一条验收标准。

## 14. 三大特别标注 (老板点名要标的)

### (a) 🔴 NPU 实测 latency 是最大未知数

- **状态**: 原厂**从没公开跑过 YOLO**。讯飞 2026-05-28 那台 ARS45 眼镜跑的是语音识别/翻译/唇语/降噪, 不是目标检测。所以这不是保密问题, 是**没人跑过**。
- **公开渠道能拿到的**: 只有 "6 TOPS" 标称值 (不可用于推延迟) + Rockchip 同段位横评 (RK3588 15.1ms / RK3576 15.4ms, 口径未标明是纯 NPU 还是 SDK 总)。
- **我方唯一实测参照是不同平台的 A733**: 纯 NPU 27.19ms (3 TOPS) → 折算到 6 TOPS 同类约 15-20ms, **置信度中**。
- **影响**: §10.5 结论 3 表明 NPU 每跨过一个 16.67ms 台阶, 端到端就多一整个帧周期 (16.7ms)。这是**全项目最大的单点风险 (R1)**。
- **动作**:
  1. Q8 (已发) 必须明确问"纯 NPU 还是 SDK 总耗时", 不能只问"多少 ms"。
  2. **投板后第一件事就是跑 NPU 基准**, 不是先做 OD 集成。
  3. 预先写好收敛路径: ① INT8 直通 ② yolov5n ③ 512×512 输入 ④ 降 OD 帧率 (需 Q2 拍板)。
  5. **在我拿到实测数之前, 任何"60fps 能跑"的结论都是没有依据的。**

### (b) 🔴 纯 NPU 耗时 vs SDK 总耗时必须分开报

- **A733 实测 (E1)**: `vip_run_network` **27.19ms** (纯 NPU) vs `awnn_run` total **36.51ms** (SDK 总), 差值 9.29ms = `tensor_to_fp` **INT8→FP32 软件反量化, 占 25%**。
- **为什么在本项目是生死线**: 帧周期只有 16.67ms。纯 NPU 若 15ms + 反量化 9ms = 24ms → **单帧就超一个帧周期**, 60fps 配置直接不成立。
- **横比陷阱**: RK3588 的 15.1ms 是哪个口径? 如果是纯 NPU 而我们报 SDK 总, 结论会错一个量级级别。
- **落地**: M3-R2 硬性要求代码里两个独立计时点 + 独立输出; §11.2 打点表 `t_npu_pure_end` / `t_npu_sdk_end` 两个字段; Q9 追加提问 ①②③④ (见 §4.3)。
- **附带**: A733 还测出 NPU SRAM→DRAM 的 DMA bridge 只有 **830 MB/s** (vs LPDDR4 理论 12.8 GB/s, 差 16 倍), 导致 FP32 输出拷贝 3 段共 40ms。→ **如果 Art.Galaxy 走类似的 FP32 输出路径, 这会是比反量化更大的坑。** 必须问清楚输出是不是 DMA 直通。

### (c) 🔴 显示输出接口未定 → 显示合成层怎么写

- **状态**: Q16 未答。"ARS45 原生带 MIPI-DSI TX" 只是媒体二手报道, 官网产品页对显示接口只字未提。可能: ① 有 DSI TX ② 只有 DP TX ③ 两者都有。
- **影响面**: 不只是"用哪个驱动", 而是 **buffer 物理内存分配方式 / 像素格式 / 延迟 / 功耗 / BOM 多一颗芯片 / 采购周期 4-8 周**。
- **我的做法 (接口隔离, 见 §7.2)**:
  - `DisplayCompositor` (合成层) 与 `DisplaySink` (输出层) **分成两层, 中间用纯虚接口隔开**。
  - 合成层 90% 的代码 (画框 / 坐标映射 / 框龄追踪 / 标签) **与 TX 类型无关, 现在就写, 用 PC 端 mock Sink 做单元测试**。
  - 像素格式做成**可配参数** (NV12 / RGB888 / RGB565), 因为桥芯片厂商参考设计会指定格式。
  - **buffer 物理内存分配下沉到 Sink 实现里** —— DSI TX 可能要物理连续, DP 可能不要。
  - 现在就定下 `DisplaySink` 接口签名: `submit(FrameBuffer&, pts)` / `set_frame_rate(fps)` / `get_latency_ms()` (最后这个直接喂 §10 预算表)。
- **必须等 Q16 才能定**: 真正的 TX 调用 / framebuffer 物理分配 / 像素格式取值 / 桥芯片延迟与功耗 (要填回 S9/S10)。
- **不要做的事**: 不要因为接口没定就推迟合成层 —— 那部分 90% 可以先写完。
