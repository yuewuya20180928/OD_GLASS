## 2. 烧录链路 (工具 / 接口 / 权限 / 失败处理)

### 2.1 烧录对象: 三层镜像

| 层 | 内容 | 变更频率 | 变更者 | 能否只换不刷 |
|---|---|---|---|---|
| **L0 bootloader** | boot ROM 之后的引导程序 + 分区表 | 极低 (原厂升级才动) | 原厂 | 否, 需专用工具 |
| **L1 系统** | kernel + DTB + rootfs (含 systemd、驱动、ISP/NPU 固件) | 中 | sw-lead | 是 (只重刷 rootfs 分区) |
| **L2 应用与模型** | OD 应用 + yolov5s INT8 权重 + ISP 参数集 | 高 (ISP tuning 十几轮) | sw-lead | **是 (ADB push, 目标 <2min)** |
| **L3 版本块** | 版本串 + 校验 + bootable 标志 + A/B 槽计数 | 每次烧录都写 | 烧录脚本 | — (最后写, 原子) |

> `[实测]` A7S 经验 (平台不同, 仅类比): 模型权重是**变更频率最高、体积最小**的一项 → 把它放在可热换的分区里, 是让 "换模型不拆眼镜" (M8-R1) 成立的唯一办法。

### 2.2 两条物理链路

```
                        ┌──────────────────── Type-C (外露, HW-09, 锁死 #15) ───────────────────┐
                        │                                                                     │

        │ L-A 量产 / 救烧路径            │                     │ L-B 调试 / 日常升级路径           │
        │ 主机: PC + 厂商下载工具         │                     │ 主机: PC + adb                  │

### 2.4 权限模型

| 模式 | 触发 | ADB | ADB root | fastboot / 下载模式 | 使用者 |
|---|---|---|---|---|---|
| **dev (研发)** | 烧录时写 `devmode=1` 标志 | 开 | 开 | 开 | sw-lead / 联调 |
| **prod (量产)** | 烧录时写 `prodmode=1` 标志 | **关** (或只读 export) | 关 | 关 (或仅限维修工位) | 产测 / 返修 |
| **service (返修工位)** | 返修流程临时开 | 开 | 开 | 开 | 返修工程师 |

**规则**:
1. **prod 模式必须关闭 `adbd`** —— 量产成品插上 USB 不应出现任何设备。虽然锁死 #11 无无线, **USB 是唯一物理攻击面** (谁拿到眼镜谁就能插线), 且量产眼镜会被别人拿到 → adbd 必须关。`[推算]`
2. **prod 模式必须关闭 fastboot / 下载模式入口** —— 防止任何人把整机刷成砖。代价是**返修必须走 service 模式** → 返修工位要有固定的解锁手段 (见 §5.2 第 1 步, 建议用一次性工单口令或物理 BOOT 组合)。`[推算]`
3. **prod 模式下只保留 CDC-ACM 串口** (或干脆不暴露) 用于产测取日志 —— 产测要拿打点 CSV (`M8-R3`), 取完即关。`[推算]`
4. **不做 secure boot 相关的权限设计** —— 签名/密钥机制 `[0数据]`, 原厂回复前不设计, 避免设计了以后推倒。`[0数据]`
5. **权限开关位存在哪 = 版本块的一部分** (`mode` 字段), 烧录脚本最后一步写入, 与版本串同区块 → 原子生效。`[推算]`

> ⚠️ **权限位写错 = 量产眼镜变砖**: 若 prod 模式写错成"关 USB PHY"级别的误伤, 返修只能拆机 JTAG。→ 故 §5.1 第 9 步必须做**出厂后回读验证** (插线确认无 adb 设备 + 确认 service 模式可进)。

### 2.5 失败处理

#### 2.5.1 失败码表 (烧录脚本统一返回码)

| 码 | 失败点 | 现象 | 自动处理 | 人工处理 |
|---|---|---|---|---|
| **F1** | USB 枚举失败 | 工具报 no device / `adb devices` 空 | 重插 3 次; 换线 (必须是数据线, 充电线无 D+/D-); 换 USB 口 | 确认 BOOT 模式电平; 核对 USB PHY `[0数据]` |
| **F2** | 写入中断电 | 分区半写 | **不自动重试** (半写状态未知) → 走全量重刷 | 全量重刷 |
| **F3** | 版本块与镜像不匹配 | 能启动但版本对不上 | 读版本块 CRC → 不匹配则拒绝启动 | 重刷 L1 |
| **F4** | 模型 hash / 格式版本不匹配 | OD 进程起不来或输出乱码 | 启动自检拦截 → 明确错误码 `E_MODEL_MISMATCH` | 重刷 L2 |
| **F5** | rootfs 挂载失败 | kernel panic | 串口 log 抓取 | 重刷 L1 |
| **F6** | **标定数据丢失** | 能开机但画质退化 (LDC/ISP 参数没) | 启动自检比对标定 ID → `E_CALIB_MISSING` | **从工厂备份恢复标定数据** (§5.2 第 2 步) |
| **F7** | bootloader 损坏 | 任何模式都不启动 | 下载工具报校验错 | JTAG / 返厂 (§4.4 S3/S4) |
| **F8** | A/B 槽状态不一致 | 启动版本不确定 | boot 计数 + 槽标志位判定 | 指定槽重刷 |

#### 2.5.2 断电原子性 (这是烧录可靠性的核心)

烧录顺序必须是**"先内容、后标志"**:

```
  ① 写 L0 bootloader
  ② 写 L1 kernel + DTB + rootfs
  ③ 写 L2 应用 + 模型 + ISP 参数集
  ④ 写版本块 payload (版本串 + 各分区 CRC/SHA256 + SN + 标定 ID)
  ⑤ 最后写版本块 magic 'AR45' + bootable 标志   ← 只有这一笔是"生效开关"
```

- **bootloader 必须在启动时校验 bootable 标志 + 各分区 CRC** → 任何一笔中断电, 结果是"不启动"而不是"启动了但半残"。`[推算]`
- **具体 bootloader 是否支持 CRC/SHA256 校验 = `[0数据]`** (原厂问题 3 第 3 问已问"是否有固件分区参考设计 (含分区表与烧录流程)", 未回) → 若原厂 bootloader 不校验, 则**必须自己在 L0 之前加一层校验** (例如把校验做到 kernel 之后的 initramfs 里), 但这取决于能否改 bootloader → 同样卡原厂。

## 3. 版本号规则 + 变更记录

### 3.1 版本号规则

#### 3.1.1 顶层版本 (SWVER) — 语义化版本

格式: `MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]`

| 位 | 何时 +1 | 兼容性含义 | 是否需要重刷 |
|---|---|---|---|
| **MAJOR** | ① flash 分区布局变了 ② 启动接口/bootloader 协议变了 ③ 硬件不兼容 (如显示 TX 从 DSI 改 DP) | **旧镜像不再适用**, 必须全量重刷 | 必须 |
| **MINOR** | 新增功能 (新增 OD 模式 / 新增 ISP 开关 / 新增产测命令) | 向后兼容, 可增量 | 视情况 |
| **PATCH** | 缺陷修复 / 参数调优 | 向后兼容 | 通常只刷 L2 |
| **PRERELEASE** | 预发布 (`-rc1` / `-beta2`) | **禁止进产线** | — |
| **BUILD** | 源码 git 短 sha (8 位) + 脏标记 (`+g1234abc.dirty`) | 追溯到唯一提交 | — |

**强制规则**:
1. **MAJOR 一旦 +1, 旧版本号必须作废并保留在 CHANGELOG 里** —— 不允许"改了 MAJOR 但镜像还能用"这种模糊状态。
2. **PRERELEASE 版本禁止烧进量产** (产测脚本自动拒绝)。
3. **同一 MAJOR.MINOR 内, PATCH 递增不重置**。

#### 3.1.2 分项版本 (6 项)

| 字段 | 内容 | 格式 | 变更触发 | 证据 |
|---|---|---|---|---|
| `boot=` | bootloader 版本 | `<原厂版本号>` | 原厂升级 | `[0数据]` 原厂未给版本命名规则 |
| `kern=` | kernel 版本 | `<linux-ver>-<gitsha8>` | 驱动改动 | `[官方]` Linux 通用惯例 |
| `rootfs=` | rootfs 镜像构建号 | `R<YYYYMMDD>.<seq>` | 每次镜像构建 | `[推算]` 自定, 需与产线一致 |
| `app=` | OD 应用版本 | `<MAJOR>.<MINOR>.<PATCH>+<gitsha8>` | 代码变更 | `[推算]` 自定 |
| `model=` | 模型版本 | `yolov5s-int8-<fmtver>-<sha256_8>` | 换模型 / 换量化参数 / **换板端格式版本** | `[推算]` + A7S 教训 `[实测]` |
| `isp=` | ISP 参数集版本 | `ISP-<calib_id>-<rev>` | 改曝光/AWB/LDC/EIS 参数 | `[推算]` |

> ⚠️ `model=` 里的 `<fmtver>` 是**必填项**, 不能省 —— 依据 A7S 的 NBG format version 坑 (§2.3)。
> ⚠️ `isp=` 里的 `<calib_id>` 与 §2.5.1 的 F6 (标定丢失) 是同一个 ID, 两者必须能互查。

#### 3.1.3 版本串整行格式 (机器可校验)

写入 `/etc/version` (单行), 也写入 flash 版本块, 也开机显示在屏幕:

```
ARS45-SW 1.0.0+g1234abc board=EVT1 sn=ARS45-EVT1-0007 build=20261026T1930+0800 \
boot=<BVER> kern=5.10.0-gdeadbee rootfs=R20261026.3 app=1.0.0+g1234abc \
model=yolov5s-int8-ag2-<sha8> isp=ISP-CALIB-0003-r2 mode=prod calib=ISP-CALIB-0003-r2
```

**校验规则 (脚本可机械判定)**:
- 行首必须 `ARS45-SW ` + 合法 semver → 否则 `E_VER_FORMAT`
- `sn=` 必须非空且与板卡丝印一致 → 否则 `E_SN_MISMATCH`
- `model=` 的 `<sha8>` 必须等于板上模型文件的 sha256 前 8 位 → 否则 `E_MODEL_MISMATCH`
- `boot/kern/rootfs/app/model/isp` **6 个字段必须全部非空** → 缺一个 `E_VER_INCOMPLETE`
- `mode=` 与期望 (prod/dev/service) 不符 → `E_MODE_MISMATCH`

> 这 5 条校验规则就是 §2.5.3 失败注入用例 FI-4/FI-5/FI-6 的判定依据。

### 3.2 版本块 (flash 独立分区)

| 项 | 内容 | 证据 |
|---|---|---|

## 4. 回滚策略

### 4.1 三个候选方案

| | **A: rootfs 级 A/B 双分区** | **B: 只读 rootfs + 可写 overlay + 单份 app/model** | **C: 只读 rootfs + app/model A/B 双槽** ⭐ |
|---|---|---|---|
| 布局 | `rootfs_a` `rootfs_b` `app_a` `app_b` `model_a` `model_b` | `rootfs(ro)` `overlay(rw)` `app` `model` | `rootfs(ro)` `app_a` `app_b` `model_a` `model_b` `ver` |
| 存储容量需求 | 2×rootfs + 2×model | 1×rootfs + overlay + model | 1×rootfs + 2×model |
| 切槽粒度 | 整机级 | 无 | 应用级 |
| 回滚耗时 | 切槽 + 重启 (~30s) | **必须重刷** | 切槽 + 重启 (~30s) |
| 需要的存储类型 | **必须 eMMC** (rootfs 若 64-256MB) | SPI-NOR 可行 | SPI-NOR 可行 |
| PCB 面积代价 | eMMC 吃 ~25% 板面积 → **板宽 12→15mm** | 无 | 无 |
| 自动回滚 | 可 (boot 计数) | 不可 | 可 (boot 计数) |
| 实现复杂度 | 高 (要改 bootloader + 槽元数据) | 低 | 中 |
| 结构/项目冲突 | 🔴 **与 MECH 板宽/镜脚厚度冲突** | 🟢 无 | 🟢 无 |

> ⚠️ **rootfs 体积 = `[0数据]`** (未实测, 原厂未给参考 rootfs 大小)。表里"64-256MB" 是 `[推算]` 的常见 Linux rootfs 量级区间, **不是本项目数据**。
> ⚠️ **这是整个回滚策略的总分叉点**:
> - rootfs ≤ ~30MB → **方案 C 用 64MB SPI-NOR 可行**, 推荐 C
> - 30-45MB → 降级 **方案 B** (回滚只能重刷) 或 64MB→128MB SPI-NOR (面积代价小)
> - \> 64MB → **SPI-NOR 方案直接出局**, 必须 eMMC → 板宽 12→15mm → **方案 A 被动成为唯一选项, 且结构要返工**
>
> 所以: **§4.3 的推荐是条件式的, 条件 = rootfs 体积 ≤ ~30MB**。这个数必须由原厂参考设计或投板后实测给出。

### 4.2 关键论证: 为什么"完整 A/B"在本项目价值有限

这是本文最重要的一个判断, 单独列出:

1. **锁死 #11 = 第一款不上无线** → 没有 OTA, 新版本只能靠 USB 推上去。
2. 既然"推上去"这一步无论如何都要插线, 那么 A/B 双分区的收益**只剩"省掉重刷 rootfs 这一步**, 省不掉"插线"本身。
3. 而 rootfs 级 A/B 的代价是 **eMMC (板宽 12→15mm)** —— 这是**硬件返工 + 结构返工 + 采购周期**, 不是软件代价。
4. → **在"无无线 + 单台样机"的约束下, 拿硬件返工换一个"少刷一次 rootfs"的收益, 不划算。**
5. → **降级方案**: 只对**小而高变**的 app/model 做 A/B (方案 C), 把 rootfs 做成只读, rootfs 坏了走"插线重刷"兜底。

`[推算]` — 依据: 锁死 #11 + `#13 先出 1 台` + tracker 的 eMMC 面积数据 (16GB 吃 25% 板面积) + MECH 总工的板宽反馈。

### 4.3 推荐方案 (条件式)

**推荐: 方案 C (轻量 A/B)**, 条件 `rootfs ≤ ~30MB`; 条件不满足则降级 **方案 B + 128MB SPI-NOR**, 或接受 eMMC 走方案 A。

**配套 3 条工程约束**:
1. **rootfs 必须做成只读 (squashfs)** —— 可写部分 (日志 `/data/perf`、参数、日志导出) 走独立可写分区。理由: 只读系统 = 可预测 = 回滚安全 (不会被运行期写坏)。`[推算]`
2. **切槽元数据放版本块** (boot_count / try_count / active_slot), 与版本串同区块原子写 → 切槽和版本号永远一致。`[推算]`
3. **自动回滚机制**: 新版本启动后由用户态 (systemd service, OD 健康后) 写 `boot_success`; 若连续 N 次 (N=3) 未写成功 → bootloader 自动切回旧槽。**N=3 是 `[推算]`** (常见值, 需与原厂 bootloader 行为对齐 —— `[0数据]`)。

> ★ **本单新发现的第 5 个约束 (容量算术) —— §4.1 漏掉的那一条**:

> (bootloader 1 + kernel 8 + rootfs 30 + app 8×2 + model 15×2 + isp 1 = 90MB) →
> **64MB SPI-NOR 装不下**, 哪怕 rootfs 压到 30MB 以内也一样装不下。
> ⇒ 推荐 C 的真实条件是 **`rootfs ≤ 30MB` 且 `flash ≥ 128MB`**; 若硬件只给 64MB, 则 app/model A/B 双槽必须缩 (或 rootfs 降到 ~20MB), 否则 §4.1 结论要改。
> **可复现**: `python3 SW/tools/flash_layout_check.py --config SW/tools/s2_rescue_config.example.json --device-size 64MB` → LAY-03/LAY-04 FAIL。
> 证据: `[实测]`(PC 侧布局检查, 2026-10-27) + 容量算术为 `[推算]` (分区大小取自 §4.1 的量级假设)。

### 4.5.2 SOP-1 — 进 BOOT 模式 (按键 / 时序 / 引脚)

#### 4.5.2.1 通用时序 (参数化, 具体数值待 P1)

```
  状态:  设备未上电 / 已断电
   │
   │  t0 ───────────── 设备上电 (或从休眠唤醒)
   │                   ★ 关键: BOOT 引脚必须在 RESET 之前就位
   │  t0+t1 ────────── 建立 BOOT 条件
   │                     方式 A: BOOT 引脚拉高到有效电平 (经测试点/跳线)
   │                     方式 B: 按住 BOOT 组合键
   │                     方式 C: 插线时主机侧拉起某个信号 (若平台支持)
   │  t0+t1+t2 ──────── 按下 RESET (脉冲宽度 t3)
   │                     ★ 部分平台要求 RESET 上升沿后 BOOT 条件仍保持 ≥ t4
   │  t0+t1+t2+t4 ──── 释放 BOOT 条件 / 按键
   │  t0+t1+t2+t4+t5 ─ 设备开始 USB 枚举 (超时 t_enum_timeout, 建议 ≥15s)
   ▼

| `t2` | 建立 BOOT → 按 RESET 的间隔 | **待 P1** | `[0数据]` |
| `t3` | RESET 按键脉冲宽度 | **待 P1** (常见 100ms 级) | `[0数据]` + `[推算]` (量级) |
| `t4` | RESET 释放后 BOOT 条件保持时间 | **待 P1** | `[0数据]` |

#### 4.5.2.2 三种进入方式 (选型表)

| 方式 | 操作 | 适用前提 | 优点 | 风险 / 代价 | 建议 |
|---|---|---|---|---|---|
| **A. BOOT 引脚 + RESET 键** | 断电 → 短接 BOOT 测试点到有效电平 → 上电 → 按 RESET → 释放 | HW-21/22 预留了 BOOT 测试点 (硬件侧 HW-22 明确要求"各电源轨/关键信号测试点") | **不依赖 bootloader 按键逻辑**, 与固件版本无关, 最可靠 | 产线要带跳线夹; 用户侧做不了 | ⭐ **产线/返修工位首选** |
| **B. 按键组合** | 按住 BOOT 键 + 按 RESET (顺序/时长待 P1) | 原厂 bootloader 支持 | 用户/售后可自助 | 与售后手势可能冲突 (见下); bootloader 改版可能失效 | 次选, 仅当 P1 明确支持 |
| **C. USB 触发** | 插线瞬间主机侧拉某个信号 | 原厂支持 "插线进下载" | 无需按键 | 依赖 PC 端工具行为, 不可控 | 不作产线依赖 |

> ⚠️ **与售后手势的冲突检查 (必须做, 否则用户误触变砖)**:
> `FRAMEWORK/AFTERSALES.md` §2/§3 已经占用侧键两个手势 —— **长按 10 秒 = 关机**, **长按 3 秒 = 显示版本号**。
> 若 BOOT 组合复用同一颗侧键, 三者在时间轴上重叠 (3s < 10s), 必须让 bootloader 做**长按阈值分层**, 否则:
> - 用户想看版本号 → 顺手插线 → 进了 BOOT → 眼镜"变砖" (只是看起来像砖);
> - 用户长按关机 → 误进 BOOT → 开机不工作 → 报修。
> ⇒ **建议 BOOT 走方式 A (独立测试点/跳线), 不复用侧键**; 若必须用键, 则 BOOT 键必须是**独立按键** (HW-22 预留 ≥2 个按键焊盘, 够用: 1 个侧键 + 1 个 BOOT 键)。
> 这条已并入 `needs_from.fw_boot_mode_hw` (给 hw-lead) —— **要一条独立 BOOT 通路, 不要挤侧键**。

#### 4.5.2.3 怎么确认"我真的进了 BOOT" —— 3 条独立证据

| 证据 | 内容 | 怎么取 | 强度 | 工具 |
|---|---|---|---|---|
| **E1 枚举特征** | BOOT 态的 USB VID:PID / product 字符串 **与正常态不同** | `lsusb` / `/sys/bus/usb/devices` | ⭐⭐⭐ 最强 | `SW/tools/boot_rescue_probe.py` |
| **E2 日志特征** | 串口/内核日志出现 `bootloader` / `u-boot` / `fastboot` / `dfu` / `download mode` | `dmesg` 尾部 / CDC-ACM 串口 | ⭐⭐ | `boot_rescue_probe.py` (自动扫) |
| **E3 引脚电平** | BOOT 引脚实测电平 = 有效电平, 且 RESET 脉冲符合时序 | 万用表 (静态) / 逻辑分析仪 (动态) | ⭐⭐ | 硬件侧 (L2) |

> **判据**: E1 与 E2/E3 **至少一条成立**, 且 E1 成立时才算"确定进 BOOT"; E2 单独成立只能判 `BOOT_SUSPECTED_BY_LOG` (**不算过** —— 探针脚本对此返回 `rc=1`, 防止用日志猜)。
> **对照**: 正常态也要采一次基线 (VID:PID + 日志特征), 否则"变了"无从谈起 → 采基线是 BR-01 的第 0 步。

**执行命令**:

```bash
# 进 BOOT 之前: 采正常态基线
python3 SW/tools/boot_rescue_probe.py --config SW/tools/s2_rescue_config.example.json --out /tmp/s2_normal.json

# 进 BOOT 之后: 再采一次 (两条输出对比 = E1 的"变了"证据)
python3 SW/tools/boot_rescue_probe.py --config SW/tools/s2_rescue_config.example.json --out /tmp/s2_boot.json
```

> ★★ **本单 L1 阶段的实际收获 (不是走过场)**: 仿真器**当场抓出我自己写的 4 个真 bug** —— 全部在"版本块"这一块:
> ① **A/B 槽 CRC 串台**: 写侧把 app_b 的 CRC 覆盖了 app_a 的 (只有活动槽才该占 CRC 槽) → 回读必然对不上;
> ② **payload CRC 把 bootable 开关算了进去**: magic/flags 是"最后一步"才写的, 它一变 CRC 必然对不上 → 改成**排除 flags 字节**的两段覆盖;
> ③ **擦除态 0xFF 被误判成 bootable**: 半写状态的 flags=0xFF, `0xFF & 0x01 = 1` → **"未生效"会被误判成"已生效"** —— 这是最危险的一个 bug, 投板后才暴露就是一次批量刷砖;
> ④ **长度字段 0xFFFF 被当成"版本串非空"** → 半写状态居然能通过 CB-03。
> ⇒ **结论: §2.5.2 的"先内容后标志"不是一句口号, 它在实现上有 4 个坑, 现在就挖掉了 4 个。** 这 4 条同时是 §2.5.3 失败注入用例 FI-3 的实现依据。

### 4.5.7 失败怎么办 (S2 → S3 → S4 决策树)

| 现象 (哪条 CB 挂了) | 最可能的原因 | 立即动作 | 上限 |
|---|---|---|---|
| 进不了 BOOT (E1/E2/E3 全无) | BOOT 通路/时序错 (P1) / BOOT 引脚电平不对 | 查 L2-1/L2-2 的波形; 换方式 A/B 试 | S2 重试 **≤2 次** |
| 枚举了但工具不认 | 协议不匹配 (P3) / 线不是数据线 / 工具版本不对 | 换线换口; 核对工具版本; 走另一条分支 (T1/T2/T3) | ≤2 次 |
| 识别了但写不进去 | 存储类型与分区表不匹配 (P4) / 中途断电 (F2) | **不自动重试** (半写状态未知) → 全量重刷; 仍失败 → S3 | ≤2 次 |
| 刷完起不来 | bootloader 校验失败 / 分区表错 (P4) / magic 缺失 | `flash_writer.py verify` 看是不是"未生效"; 是 → 重刷; 否 → S3 | ≤2 次 |
| 起来了但画质退化 | **标定数据丢失 (F6)** —— 返修最大坑 | 从出厂台账按 SN 恢复标定 + 重刷 L2 (CB-07) | 按 §5.2 第 5 步 |
| 起来了但 OD 不出框 | 模型 hash / 格式版本不匹配 (F4) | 重刷 L2 + 核对 `model=` 版本串 | 按 §2.5.1 F4 |

> 🔴 **硬规则 (与 §5.1 "失败即停"同源)**: **S2 连续失败 2 次 → 必须升级 S3 (JTAG), 不得"多刷几次试试"**。
> 半写状态反复覆盖会制造更复杂的问题 (F2 已说明)。升级 S3 由**项目总工**裁决, sw-lead 不自行升级。
> **S2 全链路失败 = 该板判"进 S4 返厂"**, 不得进产线。

### 5.2 返修烧录 (PC-FW-02)

| 步 | 动作 | 判据 / 验收 | 证据 |
|---|---|---|---|
| **1** | **故障定级**: ①纯软件 (可开机) ②系统损坏 (进不去系统但能进 BOOT) ③全砖 (BOOT 也进不去) | 三选一, 决定后续路径 | `[推算]` |

| **3** | 进 service 模式 (解锁 fastboot / 下载模式) | 工具能识别设备 | 依赖 §2.4 + 原厂工具 |
| **4** | **重刷范围按故障级选**: ②级 → 全量重刷 (L0+L1+L2, 与出厂同流程); ①级 → 只重刷问题层 (通常 L2) | 重刷范围记入返修单 | `[推算]` |
| **5** | **恢复出厂标定数据** (从第 2 步备份或从工厂标定台账按 SN 重新取) | **标定 ID 与出厂记录一致** → 否则 `E_CALIB_MISSING` | `[推算]` — F6 故障的对策 |
| **6** | 重跑 §5.1 第 8 步自检 + 第 10 步产测 | 全过 | 同上 |
| **7** | **版本记录 + 追溯**: 烧录后版本串、标定 ID、SN 写入返修单; **关联故障现象与根因**; 若走了回滚, 在 CHANGELOG 追加回滚条目 (§3.3.1) | 字段齐全 | §3.5 |

**返修与出厂的关键差异 (3 条)**:
1. **返修必须能恢复标定数据, 出厂不需要** (出厂时标定数据是现场生成的)。
2. **返修的板子状态不可信** —— 可能是上次烧录中断电的半写状态 → 返修默认**先全擦再全刷**, 不做增量刷 (增量刷的前提是"已知当前状态", 返修时这个前提不成立)。
3. **返修必须写 mode=service 还是 prod?** → **默认 prod** (返修完是给客户用的), 但要**留 24h 的 service 窗口**便于"修完又坏"的快速复现。`[推算]` — 若产线觉得不便, 可改为"返修出厂即 prod, 需要时用产线工位工具临时进 service"。
