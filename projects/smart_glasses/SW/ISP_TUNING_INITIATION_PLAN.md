## 3. RK3572 专属风险 + 为什么 tuning 必须在目标板做

### 3.1 RK3572 专属风险 (4 条)

| # | 风险 | 后果 | 证据 |
|---|---|---|---|
| R1 | ★**RK3572 专属 BSP / ISP tuning 不公开** (公开的只有通用 BSP kernel 6.1 与 rkaiq 本体) | ★**没有"抄 RK3572 官方 IQ"这条路** ⇒ tuning 只能从零标或买 | `[实测·既有记录·HW/OPEN_SOURCE_AVAILABILITY.md §4 / SW/DEMO_OD_PIPELINE_SPEC.md §4.2]` |
| R2 | ★**ISP 代不对就整个不认**: RK3572 = ISP3 ⇒ 只吃 `isp3x/` 目录里的 **json** | 拿 `isp20/` 的 xml (isp2.0 代) = **格式/目录都不对**, rkaiq 起不来 | `[实测·本机快照]` + `[实测·HW/IMX415_DEMO_SENSOR_FACTS.md §3.1]` |
| R3 | ★**rkaiq / BSP 版本漂移**: IQ json 结构与 rkaiq 版本走 | 换 BSP 版本 ⇒ 可能要重调 (白做一遍) | `[推算]` |
| R4 | ★**isp3x 目录本身很薄**: 本机既有实测记录: `isp3x/` **一共只有 10 个 .json** | ★**指望"公开仓里啥都有"是不成立的** ⇒ 现成 IQ 的覆盖面比想象窄 | `[实测·HW/AR0234CS_RK3572_PORT_SPEC.md §C6/§(isp3x 10 个 .json)]` |

### 3.2 ★为什么 tuning **必须在目标板 (RK3572 + 我们的镜头/模组/档位) 上做** —— 5 条硬绑定

1. ★**sensor × 镜头 × 模组 三者绑定** (`ISS-139` desc) —— 换镜头就换 IQ, 没有"通用版"。`[实测·ISS-139 desc]`
2. ★**ISP 代绑定** (isp3x vs isp20/isp32) —— 见 R2。`[实测·本机快照]`
3. ★**分辨率绑定**: IQ json 头 `sensor_calib.resolution` **明写 3840×2160**; mesh 目录名**锁死 3840_2160** ⇒ ★**裁到 1080p60 不能直接用** (四角/边缘色彩与亮度校正会偏)。`[实测·HW/IMX415_DEMO_SENSOR_FACTS.md §3.1/§3.2]`
4. ★**帧长 / 曝光表绑定**: 1080p60 走 binning + VMAX 3165→1582 ⇒ ★**最大曝光时间减半 ⇒ `exposure_index` 表要按新行时间/帧长重算**。`[实测·facts §2.4]` · `[推算·facts §3.3]`
5. ★**拿 RK3588 的 IQ 直接套 = 前 4 条全踩** (ISP 代可能对、sensor 不同、镜头不同、分辨率不同、曝光表不同) ⇒ ★**"网上找个 IQ 塞进去"这条路不成立**。

⇒ ★**一句话**: ★**tuning 不是"下载一个文件", 是"在目标板 + 目标镜头 + 目标模组 + 目标档位上跑一次标定"** ⇒ 所以它**占人天也占样机窗口**, ★**不能默认它会自己发生** (`ISS-139` desc 原话)。

## 4. 验收判据 (★写成"怎么量", 不许只写"达标")

### 4.1 画质四问 (A 组)

| 判据 | ★怎么测 (步骤) | ★量化口径 | 判据阈值 |
|---|---|---|---|
| **A-1 白平衡 / 色温** | 灰卡在 **4 个色温档** (2856K / 4000K / 5500K / 6500K) 各拍 **N=20 帧**; 取 AWB 收敛后灰卡 ROI 的 R/G/B 均值 | `R/G`, `B/G` 比值 (去曝光归一) + **收敛帧数/收敛时间** | **阈值待首轮标定板实测定** ⇒ 先**记录**不设门限 (`SW/DEMO_OD_PIPELINE_SPEC.md` §5.4 同口径) `[推算·待校准]` |
| **A-2 暗角 (vignetting)** | 均匀光源下拍 ≥5 帧; 中心 ROI vs 四角 ROI 亮度均值 | `角落均值 / 中心均值` | 阈值待实测; ★**120° 鱼眼要单列** (标定板只能覆盖 ±40° ⇒ 边缘靠均匀光源测, 不靠棋盘格) `[实测·SW/FISHEYE_GEOMETRY.md:301]` · `[推算·待校准]` |
| **A-3 噪点** | 固定曝光 (`exposure_us` 锁死) 暗场拍 ≥50 帧; 平坦 ROI | `σ/μ` (SNR) + **量化饱和率** (0 与 255 的像素占比) | 阈值待实测; ★**饱和率是 B 组的先行指标** `[推算·待校准]` |
| **A-4 动态范围** | 亮档 / 暗档各拍 | 直方图截断率 (0% / 100% 像素占比) | 阈值待实测; ★**直接决定后处理阈值会不会被搞坏** (见 B-4) `[推算·待校准]` |

### 4.2 ★与 OD 模型输入分布一致 (B 组) —— ★这一条必须"用 OD 真正吃到的输入去量"

> ★**机理 (为什么 ISP 搞坏后处理阈值 ⇒ 端到端精度塌)**: OD 的 score 阈值 **0.3** 与 NMS IoU **0.45** 是在 **COCO 分布**上定的 (`SW/DEMO_OD_PIPELINE_SPEC.md` §3.4 / §1.4) ⇒ ★**ISP 若整体压暗 / 偏色 / 压动态范围 ⇒ 特征响应幅度整体变 ⇒ score 分布整体左移 ⇒ 0.3 这条线要么放过一堆误检 (FP 激增) 要么把真目标全砍掉 (Recall 掉)** ⇒ ★**端到端 F1 塌**。⇒ ★**"出图看着正常"完全测不出这件事** —— 必须量分布。

| 步 | ★怎么量 | 口径/工具 |
|---|---|---|
| **B-1 采样** | ISP 实拍 **≥200 帧** (4 色温 × 3 照度 × ≥15 帧), **存 NV12 原始帧** (不转码) | 与 demo 管线同一条 capture 路径 |
| **B-2 预处理** | ★**与板端逐字一致**: 取 Y 平面 (或 I420→RGB) → letterbox **640×640 (pad=0 黑边)** → **/255 (值域 [0,1])** → NCHW float32 | `[实测·SW/DEMO_OD_PIPELINE_SPEC.md §2.2]` (与 `SW/tools/rknn_bench.py::preprocess()` 对齐) |
| **B-3 分布统计** | 逐通道 **mean / std / p1 / p5 / p50 / p95 / p99** + **饱和率** (0 与 1 的占比); 对比**量化校准集** `calib_yolov5_100` (同一批 COCO val, letterbox 640×640 黑边) 的同名统计量 | `[实测·SW/DEMO_OD_PIPELINE_SPEC.md §1.4 口径]` |
| **B-4 判据 (量化)** | ①逐通道 `|Δmean| ≤ 0.05` (值域 [0,1]) ②`std` 比值 ∈ **[0.7, 1.4]** ③饱和率差 **≤ 2 个百分点** | ★**阈值为 [推算·待首轮实测校准]** —— 首轮拿到数据后**写死**并回填本节 |
| **B-5 端到端收口** | 自采**有标注**实拍集 ≥100 张, 按 §3.4 同口径 (逐类 IoU 0.5 贪心 / NMS IoU 0.45 / **score ≥ 0.3**) 算 P/R/F1 | ★**判据 = F1 ≥ 0.25 (demo 线, ISS-164 已裁决) 且 Recall 不出现系统性塌陷** (ISP 坏掉时最典型的形态 = Recall 掉 + FP 不涨) |

★**B-5 为什么必须用"有标注实拍集"**: §1.4 的 F1 数字 (yolov5n = **0.2927** / yolov5s = **0.3017**) 是 **COCO val2017 前 300 张** 上的, ★**不能和 ISP 实拍帧直接比** (没有同一批标注) ⇒ ★**只能同口径各自测, 再比"掉没掉"**。`[实测·§1.4]`
★**本节的统计脚本还没写** (要板端帧) ⇒ ★**列为本单后续**, 板端不可达期间一律 `[0数据]`。
