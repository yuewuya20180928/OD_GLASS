**为什么先复用不重训 (三条理由, 都不是"没时间")**:
1. ★**口径一致**: 老板 11-02 定的 demo 就是 "80 个常见目标类" ⇒ 与 A7S 的 80 类**同口径** ⇒ 精度评测脚本 (`rknn_bench.py acc` / `eval_od_accuracy.py`) 一行不用改就能用。
2. ★**量化损失可量化且很小**: ΔF1 = −0.0043 (实测, 300 张) ⇒ 重训在 demo 阶段买不到精度。
3. ★**demo 的目的是"打通链路", 不是"刷 mAP"** —— 一旦进入整机阶段, 眼镜场景 (120° 鱼眼 + 近距离 + 运动模糊) 的 mAP 会与 COCO 差很远, 那时才需要**眼镜场景校准集 + 重训**; 现在重训 = 重训一个还没验证的管线。

### 1.2 ★★ 必须说清楚的一件事: 仓库里的 80 类资产是 **yolov5s**, 不是 yolov5n

> **老板派单时写的是 "A7S 那套 yolov5n INT8 量化流程与 80 类口径"**。核对台账后的实际状态:
> - ★**唯一被转换 + 被实测过的板端模型是 `MOD-YOLOV5S-640-ARS45-SRC`** (`~/Public/radxa_yolo/acuity_pipeline/model/yolov5s-sim.onnx`, sha256[:16] = `20368be665f6f59a`, 640 输入, 29,337,706 B) ⇒ `SW/MODEL_ASSETS.md` §1.2 · [实测]
> - ★**yolov5n 在本仓库里只有第三方 benchmark 数字, 没有模型资产**: RKNN model_zoo 性能表 RK3576 `yolov5n@640 INT8 = 112.7 FPS = 8.87 ms` (`SW/RKNN_BENCH.md` §4.2) · [公开实测·第三方]
> - ⇒ **可复用的是"流程"(calib → convert → sim → acc 四步链), 不是"yolov5n 这个模型"**。

**因此本单写死的模型路线是二选一, 并给出判据**:

★**本单对模型路线的写死结论**:

### 2.5 板端进程结构 (规格, 不写代码)

```
[1 个采集线程]  V4L2 / rkisp 取帧 → NV12 帧队列 (深度 2~3, ★见 §5.4 buffer 数推导)
[1 个 OD 线程]   取帧 → 预处理 → rknn_run → decode/NMS → 画框(Y 平面) → 提交 DRM plane
[1 个显示线程]  或由 DRM/KMS 的 vblank 事件驱动 page flip
```

★**帧队列深度取 2~3 的理由**: 深度 1 ⇒ 采集与推理串行, 推理慢就掉帧; 深度 ≥4 ⇒ 端到端延迟被排队拖长 (框龄变大)。demo 阶段先用 **2**, 实测后调。
★**buffer 内存占用推导** (P1 路径): NV12 1920×1200 = 2.76 MB/帧; 队列 2 帧 + OD 输入 640×640×3 float32 = 4.9 MB + 推理输出 (3 路 head: 640² + 320² + 160² = 512000 框 × 85 float ≈ 174 MB —— ★**这个数很大, 必须用 INT8 输出或只取 3 路 head 的必要字段**, 否则 demo 板内存爆) ⇒ ★**[待核] 板端 rknn_outputs_get 是 INT8 直通还是反量化后的 FP32** —— 这直接决定内存与 `t_sdk_total` 的构成, 是 A733 实测里那 9.29ms 反量化的同一件事 (见 §5.2)。

## 3. 后处理与画框

### 3.1 ★★ 坑①: 画框画在哪一层 —— 写死

**结论: 框画在 NV12 的 Y (亮度) 平面上, 不碰 U/V 色度平面。**

**理由 (三条, 逐条对应老板 11-02 的 ①)**:
1. ★**色度不同步**: YUV420 的 U/V 平面是 **4:2:0 半分辨率**, 且色度采样点的位置与亮度像素 **不同格**。若在 Y 平面画框、在 U/V 平面也画色, 两条边的色度坐标必须各自做 4:2:0 采样位置修正 —— 少做一步就是**框偏色**, 做错就是**框错位 1 个色度采样格 (2 个亮度像素)**。
2. ★**只画 Y ⇒ 框是"亮度对比"的灰阶框**: 对**单色面板**同样有效 (而且面板**单色还是全彩尚未确认** —— `state/outbox/visionox_display_inquiry.md` Q1, ★**草稿未发**, 这题决定产品定义), 对全彩面板则是灰/白框。
3. ★**省带宽与 CPU**: 全彩框要求先转 RGB24 (1920×1200×3 = 6.9 MB/帧) 再画, 再转回 NV12 送 DSI ⇒ 每帧多 2 次全帧转换。**demo 阶段不值得**。

**先后顺序 (★本单写死的唯一顺序, 不可调换)**:

```
ISP NV12 (W×H)
   │
   ├─(A) 预处理: 取 Y → RGB → 等比 letterbox 到 640×640 (黑边) → /255 → NCHW float32
   │
   ├─(B) 推理: rknn_run (INT8)
   │
   ├─(C) 后处理 (CPU): decode 3 路 head → score = obj × cls.max → score ≥ 0.3
   │                   → per-class NMS (IoU 0.45) → 框列表 (仍在 640×640 坐标系)
   │
   ├─(D) ★坐标反变换 (映射, 不是画框): 640×640 → 帧坐标系
   │      P1: x_f = (x_od-0)×3 , y_f = (y_od-120)×3
   │      P2: x_f = (x_od-0)×1 , y_f = (y_od-80)×1
   │
   ├─(E) ★画框: 直接写 NV12 的 Y 平面 (U/V 一律不动)
   │
   ├─(F) (可选) YUV420 → RGB24 转换 (仅当 DRM plane 格式要求 RGB 而不能吃 NV12 时)
   │
   └─(G) 显示: 等比 letterbox 到 1920×1080 → DRM/KMS plane 提交 → DSI TX
```

★**为什么 (D) 在 (E) 之前、(E) 在 (G) 之前**: (D) 是纯算术, 不产生像素; (E) 必须在**帧坐标系**上画, 因为框是"物体在哪"的语义; (G) 是一次几何变换, 会把整张图 (含框) 一起缩放 —— **框与内容因此天然保持对齐**。

★**如果将来必须要彩色框**: 改 (F) 为 "YUV420 → RGB24 → 在 RGB 上画框 (框颜色按类别索引调色板) → DRM RGB plane"。代价 = 每帧 2 次全帧转换 + 6.9 MB 中间 buffer。**触发条件**: 老板要求"用颜色区分检测类别" ⇒ 而这恰好是 `visionox_display_inquiry.md` Q1 问面板厂的问题之一 (单色面板无法用颜色区分类别) ⇒ ★**这条需求必须等面板单色/全彩确认后才定**。

### 3.2 框的格式与颜色

| 项 | 规格 | 理由 |
|---|---|---|
| 框坐标表示 | **整数像素, 左上角 + 右下角 (x0,y0,x1,y1)**, 帧坐标系 | 整数 ⇒ 无亚像素误差; Y 平面画线只能整像素 |
| 框宽 | **2 px** (P1/P2 一致, 在**帧坐标系**里定义) | 1px 在 0.49" 高密度面板上几乎不可见 |

### 3.3 坑②: 16:10 → 16:9 的 letterbox 账 (★画框在缩放之前的原因)

**AR0234CS 1920×1200 (16:10) → 视涯 1920×1080 (16:9)**:

```
k = min(1920/1920, 1080/1200) = 0.9
内容区 = 1920×0.9 × 1200×0.9 = 1728 × 1080   (整数, 无误差)
黑边   = 左右各 (1920-1728)/2 = 96 px, 上下 0 px
```

★**为什么是左右黑边而不是上下**: 16:9 (1.778) 比 16:10 (1.600) **更宽** ⇒ 从 16:10 缩到 16:9 是**按高度缩**, 宽度富余 ⇒ 黑边在**左右**。
★**为什么走 letterbox 不裁剪**: 老板 10-25 19:33/19:42 定的 "sensor 输出不裁剪, 后级只缩放" 是硬约束 (`SW/ISP_SCALING_MODE.md` C1~C5: 禁 ROI 裁剪 / 禁 aspect crop / ISP 输入必须是 sensor 全幅) + REQ-GEO-07 "优先等比 (letterbox 加黑边)"; 而**裁剪**这条路在 `HW/DISPLAY_MODULE_DECISION.md` 已算过立体角只丢 9.70%, 但那也意味着**丢视场** ⇒ demo 阶段一律 letterbox。
★**不裁剪 ⇒ 黑边是预期产物, 不是缺陷**: 验收时黑边位置必须**精确在左右各 96px** (判据 ④)。

**P2 路径的账 (640×480 → 1920×1080)**: k = min(1920/640, 1080/480) = **2.25** ⇒ 内容 1440×1080, 黑边**左右各 240px**。

★**统一的参数化写法 (两套路径共用一段代码, 只是参数不同) —— 这是路径B→路径A 切换不引入错位 bug 的前提**:

  "capture":  { "width": 1920, "height": 1200, "format": "NV12" },   // P1; P2 = 640/480

★**阶段 1 能证明什么 / 不能证明什么** (必须写清, 免得后面扯皮):

### 4.4 分辨率与 letterbox 参数 (显示侧最终值)

| 项 | P1 (1920×1200 帧) | P2 (640×480 帧) |
|---|---|---|
| 面板 mode | 1920×1080@60 | 1920×1080@60 |
| 缩放 k | **0.9** | **2.25** |
| 内容区 | **1728×1080** | **1440×1080** |
| 黑边 | **左右各 96px, 上下 0** | **左右各 240px, 上下 0** |
| 缩放实现位置 | ★**CPU/RGA 做等比 letterbox 到一块 1920×1080 buffer, 再 1:1 送 plane** (不依赖 VOP 做非等比缩放) | 同左 |
| plane 格式 | NV12 (若 DSI 链路吃 NV12) 或 RGB888 (带宽 ×3, 373Mbps 是 RGB888 口径) | 同左 |

★**为什么缩放放 CPU/RGA 而不放 VOP**: VOP 若做 1920×1200 → 1920×1080 是**非等比** (x 1.0 / y 0.9) ⇒ 会把画面**纵向压扁 1.111×** ⇒ 违反等比原则 + 框会随内容一起被压扁 (框变形) ⇒ **必须先在 CPU 侧做成等比 letterbox 的 1920×1080 画布, 再 1:1 送屏**。
★**[待核] RK3572 的 VOP2 是否支持缩放** —— 若支持且支持**等比缩放**, 可以省掉 CPU 侧 resize, 但**那是优化不是前提**。

## 5. 帧率与延迟打点

### 5.1 ★ 打点口径的真正出处 (纠正一处派单里的口径)

> **派单写的是 "复用 `SW/tools/timing_check.py` 的端到端打点口径"** —— 核对后需要纠正:
> ★**`SW/tools/timing_check.py` 是硬件时序的算术复核器**, 内容是 复位 RC (F1) / 监督器 CT 延时 (F2) / I2C 上升沿 (F3) / ADC 建立时间 (F4) / TMP117 (F5) / USB 复位握手 (F6) / 皮肤温度分档 (F7) / 关机语义 (F8) —— **它不含端到端视频延迟打点**。
> ★**端到端延迟打点的真正出处有两处**:
> ① `SW/ARS45_INT8_CHAIN.md` **§4 (B8 埋点表)** —— 9 个打点的**名称与定义**就在这里;
> ② `SW/RKNN_BENCH.md` **§4.1 (S4~S10 分段账)** —— 每段的**占位数与端到端模型**在这里。
> ⇒ **本规格按 ① + ② 写**, 并沿用 `timing_check.py` 的**风格铁律** ("每个数必须能从原始值重新算一遍" + "退出码 0 = 自检全过")。
> ⇒ ★**不修改 `timing_check.py`** (写入边界), 它的复用方式 = **风格参照 + 后续可另立一个 `demo_timing_check.py`** (下一步, 不在本单)。

### 5.2 ★★ 铁律: 纯硬件耗时 vs SDK 总耗时 必须分开报 (SOUL.md)

**A733 实测基准 (唯一一组我们有实测的对照数)**:

### 5.5 端到端模型 (口径不变, 直接代入)

```
P60 = 16.67 ms   sensor 帧周期 @60fps
E   =  8.3  ms   曝光积分
R   =  8.3  ms   读出
S3  =  8.0  ms   ISP (含缩放)              ⇒ 曝光块 E+R+S3 = 24.67 ms  ★不可协商
S4  =  1.0  ms   预处理 (letterbox + 布局 + 归一化)
S5  =  ???? ms   纯 NPU 推理                ← demo 要测的
S6  =  2.0  ms   反量化 (A733 上占 SDK 总耗时 25% ⇒ 保守取 2ms)
S7  =  3.0  ms   decode + NMS (CPU)
S8  =  1.0  ms   画框
S9  =  3.0  ms   显示 TX
S10 =  5.0  ms   光机逐帧延迟  ★[0数据]

T_od  = S4 + S5 + S6 + S7 = S5 + 6 ms
模式 A (显示等 OD):  e2e = 24.67 + T_od + 9   = T_od + 33.67
模式 B (异步 60fps):  e2e = age×16.67 + 16.67 + S3 + 9 = (age+1)×16.67 + 17
                      age = ceil(T_od / 16.67)   ← 台阶函数
```
· `SW/RKNN_BENCH.md` §4.1 · [实测/推算]

★**台阶效应提醒 (给整机阶段, 不是 demo)**: 模式 B 下 "差 0.01ms = 差 16.67ms"。RK3572 + yolov5n 推算 T_od = 18.91ms ⇒ age = 2 ⇒ 模式 B 67.34ms ❌, **差 2.23ms 就掉档**。

## 7. ★ 两条路径对比 (AR0234CS 单线 vs 先用现成 BSP sensor)

### 7.5 ★★ 我的判断 (直接回答老板的两个问题)

**Q1: demo 链路的软件部分有多少比例与 sensor 无关?**

> ```

> ⇒ ★**"最短出画面"这个目标, 其瓶颈是面板 init code, 不是 sensor**。因为:
> ① 屏上出画面**根本不需要 camera** —— 用测试图卡/回放文件就能验 DRM/KMS + DSI + 面板 (§4.3 阶段 1);
