| 项 | 说明 |

### 0.5 通用通过判据 (所有用例共用)

| # | 规则 |
|---|---|
| 1 | 每个用例的"通过标准"必须**可机械判**: 具体数值 / 具体计数 / 具体现象。禁止"工作正常""基本正常""无明显异常" |
| 2 | 每个用例必须产出**可复现的数据文件** (路径写进 EVT 报告 §9.2), 无数据文件的用例判 ⚠️未验 |
| 3 | 每个数值必须带证据等级; 只有 [实测] 可用于准出判定 |
| 4 | 耗时类数据必须给 **min/avg/p95/max + 采样帧数**, 不接受只报 avg (A7S 教训: 只报总 fps 看不出 OD-bound) |
| 5 | 失败用例必须落成 `state/issue_log.yaml` 的一条 issue, 不许只在文档里写一句"有问题" |
| 6 | 任何用例若因外部依赖 (设备/接口/拍板) 无法执行 → 判 ⚠️未验, 写明阻塞原因与期望时限, **不许用推算值替代实测** |

| 逻辑分析仪 (可选) | 抓帧同步/中断 | ≥100MSa/s | IT-P4-04 (口径 C 起点) |

### 2.2 软件基线

| 项 | 要求 |
|---|---|

### 3.2 P1 — 上电与时钟

#### IT-P1-01 冷启动上电时序与稳定性
- **归属模块**: M1
- **主测**: sw-lead

##### 3.4.1 排除前后处理的方法 (M-NPU 口径的核心, 必读)

**要排除的两段**:
| 段 | 起止 | 为什么必须排除 |
|---|---|---|
| 前处理 (S4) | `t_isp_out` → `t_npu_call` | 含 letterbox 800×600→640×640 + 量化输入构造 (A7S `bgr.clone()` 实测 0.5ms), 与 NPU 硬件能力无关 |
| 后处理 (S7+S8) | `t_npu_sdk_end` → `t_post_end` | 含 decode+NMS+画框, 是 CPU 侧工作, 混进 NPU 耗时会让跨芯片横评失真 |

**排除手法 (四层, 按可靠性排序)**:
1. **计时点夹紧 (首选)**: `npu_pure_ms = t_npu_pure_end - t_npu_call`。前处理全部发生在 `t_npu_call` 之前、后处理全部发生在 `t_npu_sdk_end` 之后, **在时间轴上天然不重叠** → 这是排除前后处理的**结构性**保证, 不靠减法估算。
2. **输入侧隔离**: 预先构造好已量化的输入 tensor 常驻内存, 循环推理**复用同一 buffer**, 不重复做 letterbox/量化 → 前处理耗时为 0, 从源头排除。
3. **SDK 总耗时交叉验证**: `npu_sdk_total_ms = t_npu_sdk_end - t_npu_call`, `quant_overhead_ms = npu_sdk_total_ms - npu_pure_ms`。若 `quant_overhead_ms` 异常大 (如 A733 的 9.29ms / 25%), 说明 SDK 强制 FP32 输出, 必须单列报告。
4. **降级方案 (仅当 SDK 不暴露硬件段计时)**: ① 从 SDK 自带 profiling 日志中取硬件段; ② 用"INT8 直通 vs FP32 输出"两条路径的耗时差反推硬件段; ③ 用同模型空跑/减算子模型测固定开销作基线扣除 —— **方式 ②③ 得到的值标 [推算], 不能标 [实测]**, 且必须写明是反推。

**反例 (不许这样算)**: `npu_pure_ms = 整帧 OD 耗时 - 已知的 letterbox 常数` —— 用减法排除会引入常量本身的误差, 不可机械复现。
