### 1.3 皮肤侧热模型 (直接引用 `MECH_BUDGET.md` §2.3, 未改动任何参数)

```
皮肤侧温升 = P × R_skin_path × [R_conv / (R_skin_path + R_conv)]
皮肤侧温度 = 35°C (基准) + ΔT

主模型:    R_skin_path = 54.2 K/W (壳壁 12.5 + 皮肤界面 41.7), R_conv = 667 K/W (150mm², h=10)
           → 有效系数 = 54.2 × 667/721.2 = 50.13 K/W   ← 本文写 50.1
剥离口径:  R_skin_path = 41.7 K/W (只算皮肤界面), R_conv = 667
           → 有效系数 = 41.7 × 667/708.7 = 39.25 K/W
```

| 参考 | 核对 |
|---|---|
| 1.22W → +61.1°C → 96.1°C | 1.22 × 50.13 = 61.2 ✅ 与 MECH 一致 (本文写 96.2, 差 0.1°C 是四舍五入) |
| 0.23W → +11.5°C → 46.5°C | 0.23 × 50.13 = 11.5 ✅ |
| 43°C 红线 ↔ 0.16W (主) / 0.21W (剥离) | 8/50.13 = 0.160 ✅ / 8/39.25 = 0.204 ✅ (MECH 写 0.21, 差 0.006) |

### 1.4 ⚠️ 本文指出的一个建模口径错误 (MECH 未错, 是**喂进去的 P 错了**)

MECH §2.3 的热模型里, **P 应该是"贴皮肤镜腿结构件内部的发热量"**, 不是"整机功耗"。
我们 1.22W 是**整机**数字, 而 sensor (在镜框上沿) + 光机 (在镜框正中) **本来就不在镜腿里**。

→ 本文所有温度表**给两栏**: 「整机口径」(沿用 MECH 现行用法, 便于对比) 与 「镜腿内口径」(发热件都在镜腿时的真实值)。
→ **结论方向两者一致** (都 ❌❌❌), 但满载数值从 96.1°C 修正到 **80.1°C** (口径 a) —— 仍然是红线的 **1.9 倍**, 翻不了案。

## §2 ★场景换算依据 (核心章, 不许糊弄)

### 2.1 两个场景的逐项对照

| 项 | 官方口径 `[媒体]` | 我们 `[推算]` | 换算方向 |
|---|---|---|---|
| 分辨率/帧率 | 1080p **@30fps** | 1080p **@60fps** | ISP 动态 **↑ 2×** |
| EIS | **开** | **关** (tracker §0 #9, 基线按关) | ISP 动态 **↓** (EIS 是多帧运动估计+插帧) |
| NPU 推理 | **无** (只录像) | yolov5s INT8 640×640 **@60fps** | **↑ 新增 ~100-250 mW** |
| 显示输出 | **无** (录像, 不显示) | DSI **800×600@60** 叠加输出 | **↑ 新增 ~30-80 mW** |
| 录像编码 | **有** (片上 Video Codec `[媒体]` EET 原文列了 "Video Codec") | **无** (我们不录像) | SoC **↓** 100-200 mW (若官方 300mW 内含编码) |
| 写盘 | 有 (录像) | 无 | ↓ (量级未知) |
| 口径 | "**整芯片**功耗 (**含 DDR**)" | 我们的 "SoC 域" = 芯片级 (不含 sensor/光机) | ✅ **口径可比** (这是唯一的正面消息) |
| 总数 | **< 300 mW** (上限, 非定值) | **待算** | — |

> **口径对齐结论**: 官方是**芯片级含 DDR**, 我们的 500-900 mW 也是**芯片级不含 sensor/光机** → **两个数可以直接比**。之前担心的 "口径不可比" 风险不存在。

### 2.2 换算模型 (每个系数都列算式)

官方场景 (O) 与我们场景 (W) 拆解:

```
P_o = s + x + e + v          (官方: 静态 + ISP@30 + EIS@30 + 编码@30) = 300 mW  [媒体, 上限]
P_w = s + 2x + n + g         (我们: 静态 + ISP@60 + NPU + 显示输出)
     └ 官方 ISP@30 的翻倍 (关 EIS 后, 每像素基础流水线成本 ×2 帧率)
───────────────────────────────────────────────────────────────────────────
⇒  P_w = 300 + x − e − v + n + g        ← 本文所有分支都用这一条式
```

| 符号 | 含义 | 取值与依据 |
|---|---|---|
| `s` | 静态功耗 (泄漏 + DDR 自刷新 + PLL + 常驻 CPU/DSP/RISC-V) | 隐含, 由 `300 − x − e − v` 反推 |
| `x` | ISP **动态**功耗 @1080p30 (不含 EIS) | **60-150 mW** `[推算]`, **0 官方数据**。依据: 官方 250 MP/s ISP 吞吐 `@1080p60` = 124.4 MP/s, 占 49.8% `[推算]` (tracker §3.1); 官方场景 62.2 MP/s = 24.9% → 满吞吐一半时动态功耗按比例 ≈ 一半 |
| `e` | EIS 额外功耗 @1080p30 | **0-60 mW** `[推算]`, **0 官方数据**。tracker §3.1: 开 EIS 使 ISP 吞吐从 49.8% → 70-80% → EIS 吃掉的吞吐 ≈ 我们 30fps 动态功耗的量级, 故 `e ≈ 0 ~ x` |
| `v` | Video Codec 编码功耗 @1080p30 | **0 或 100-200 mW** `[推算]`, **0 官方数据**。EET 原文确认 ARS45 "集成 Video Codec" `[媒体]`; 12nm 软编 1080p30 ≈ 100-200 mW (经验量级, 无官方数据) |
| `n` | 我们的 NPU 功耗 | **100-250 mW** `[推算]`, 锚点见 §2.3 |
| `g` | 显示输出侧 SoC 功耗 (DSI TX + 缩放 1080p→800×600 + 叠加) | **30-80 mW** `[推算]`, **0 官方数据**。依据: 官网称可输出 4K@30 `[官方]`; 800×600@60 ≈ 4K 的 1/16 像素 → TX+PHY 约 20-50 mW + 缩放/叠加 |

### 2.3 NPU 项 `n` 的两种算法 (取包络, 不取平均)

**算法 1 — 能效比法** `[媒体 锚点]`:
```
能效比 = 10 TOPS/W (INT8, 12nm)   ← EET China 原文: "在12nm工艺下能耗比约为10TOPS/W"
⚠️ 原文限定语: "针对智能眼镜应用场景的 **OCR 类应用** 进行了深度优化 … 在12nm工艺下能耗比约为10TOPS/W"
我们的 NPU 工作量 = 16.5 GF/帧 × 60 fps = 990 GOPS/s = 0.99 TOPS/s
P_npu = 0.99 TOPS/s ÷ 10 TOPS/W = 99 mW
→ 乘 DVFS/利用率余量 (NPU 640×640@60 已占 ~90% 利用率, tracker §3.2) ×1.5 → 148 mW
```

**算法 2 — 媒体逐点标度法** (EET China 新证据, `[媒体]`, 之前没人用过):
```
PPOCR-Det INT8: 30 FPS → 150 mW;  10 FPS → 50 mW     (原文实测数据点)
   → 斜率 (150−50)/(30−10) = 5.0 mW/帧, 截距 50 − 10×5 = 0 mW  ← 线性过零
PPOCR-Rec INT8: 30 FPS → 75 mW;   10 FPS → 25 mW
   → 斜率 2.5 mW/帧, 截距 0 mW
⇒ 结论 1: NPU 功耗 ≈ 帧率线性, 静态分量≈0 (DVFS 线性缩放), 所以我们 60fps ≈ 2× 30fps
⇒ 结论 2: 这两个数据点**不是 MAC 数正比** (PPOCR 是轻量检测头, 远小于 yolov5s@640 的 16.5 GF/帧),
   说明它们主要含**每帧固定开销 + DDR 搬运**, 不能直接当 yolov5s 的每帧成本
⇒ 取包络: n ∈ [100 (算法1), 250 (算法2 保守外推: 我们的模型每帧比 OCR 重 ~10-30×, 保守取 2×150+)]  mW
```

### 2.4 三个分支 (每个分支都写清假设)

| 分支 | x | e | v | n | g | **P_w (SoC 域)** | 算式 |
|---|---|---|---|---|---|---|---|
| **C 乐观** | 60 | 60 | 150 | 100 | 30 | **280 mW** | 300+60−60−150+100+30 |
| **B 中** | 100 | 50 | 0 | 150 | 50 | **550 mW** | 300+100−50−0+150+50 |
| **A 悲观** | 150 | 0 | 0 | 150 | 60 | **660 mW** | 300+150−0−0+150+60 |

**分支取舍**:
- **排除 280 mW 分支**作为规划值: 它要求同时假设"官方 300mW 内含一个 1080p30 编码器 (150mW)" + "EIS 只多花 60mW" + "我们的 NPU 只要 100mW" —— 三个乐观假设叠在一起, 而且官方是否用片上 Codec 编码未知 `[0数据]`。
- **排除比 660 mW 更差的分支**: 若官方 300mW 不含编码 (`v=0`), 则 `s` 变大, 我们的静态基底也变大 —— 但 660 mW 已覆盖 `e=0` 的极端 (EIS 白嫖)。
- **规划取值**: **SoC 域 (口径 b) = 400-660 mW, 中位 550 mW** `[推算]`
- **对比现状预算 500-900 mW (中位 700)**: **上界高估 27%, 中位高估 21%, 下界高估 20%** → **我们的 SoC 预算确实偏保守, 但只是偏保守, 不是错到能翻案。**

### 2.5 ★三条"不许直接套用"的理由 (为什么 300mW 不能当我们的值)

1. **它是上限不是定值**: 原文 "**低于** 300mW" `[媒体]` → 实际可能是 200mW。若 P_o=200, 上面所有分支 **整体下移 100mW** (P_w = 200 + x − e − v + n + g) → 我们的 SoC 可能是 180-560 mW。**这个不确定性本身就大于它能带来的收益。**
2. **官方 300mW 里到底装了什么, 官方没给**: 测试条件 = **`[0数据]` (官方未给)** —— 传感器是否在测点内 / 编码是否在测点内 / 测的是哪几路 / DDR 是自刷新还是满带宽 / 芯片是 DVFS 在哪个档位, **全都没有**。→ **在测试条件回来之前, 300mW 只能当"上界参考", 不能当输入。**
3. **官方场景与我们场景是"跷跷板", 不是"叠加"**: 官方有 EIS + 编码 (耗电), 我们有 NPU + 显示 (耗电)。**只有在 EIS 成本 ≈ 编码成本时才抵消**, 而这两个数官方都没给。

### 2.6 场景换算的最终一句话

> 官方 300mW `[媒体]` 经场景换算后, 只能支撑 **SoC 域 400-660 mW (中位 550 mW) `[推算]`**; 我们原预算 500-900 mW 高估 20-27%, **但换算后的满载整机仍为 0.87-1.07W, 贴皮肤仍是 78.6-88.6°C vs 43°C 红线 → 不翻案。**

## §5 结论: 是否翻案

### 5.1 判定

| 问题 | 判定 |
|---|---|
| **满载在贴皮肤镜腿里可行吗?** | **❌ 否 (不翻案)** —— 88.6°C (口径 b 有桥) / 78.6°C (原生 DSI) vs 43°C 红线, 仍差 1.8-2.1 倍 |
| **方案C (0.23W → 46.5°C) 翻案吗?** | **❌ 否** —— 口径 b 待机-A 只降到 46.1-47.1°C, **仍超红线 3-4°C** |

### 7.3 ★哪些砍不动 (物理不可约)

| 项 | 最低可到 | 为什么砍不动 |
|---|---|---|

| **NPU (yolov5s 640@60)** | **~100 mW** | 算法工作量固定 (16.5 GF × 60 fps = 0.99 TOPS/s ÷ 10 TOPS/W); 只能降帧率或降分辨率 → 与需求 §REQ 6 (≥1080p60) 和 §REQ 7 (60fps OD) 冲突 → **不可动** |
| **ISP @1080p60** | **~60-150 mW** | 1080p60 是输入硬指标 (REQ #6); 只能关 EIS (已关) |
| **显示输出 (DSI 800×600@60)** | **30-80 mW** | 产品定义要求 (必须显示 OD 框); 只能降亮度 (光机侧, 有 JBD I2C 接口, 但光机 98mW 是 JBD 官网值, 不随亮度线性?) |
| **光机 走鹃Ⅱ** | **98 mW** `[官网]` | 器件固定; 但**在镜框不贴皮肤 → 不进皮肤账** |
| **sensor (若 sensor-only)** | **目标 ≤300 mW** | 器件未选; 见 §6 |
| **待机 (变体 B 全下电)** | **3-6 mW** | 充电管理静态 + 漏电 + 唤醒; 0.05W 是现实地板 |
| **充电 IC 耗散** | 0.8 W @1A | 与充电电流绑定; @1A 是我们主动选的 (POWER_IC_SELECTION §: 1.0A 推荐) → **充电时必须摘下眼镜**, 不可折中 |

### 7.4 结论

> **43°C (0.16W) 可以达到** —— 靠 **待机口径 0.05W + f=10% + 无桥接** (0.132W / 41.6°C), 不需要动硬件结构。
> **40°C (0.10W) 靠降功耗达不到** (NPU+ISP+显示的物理下限 ~0.19-0.28W 在 f=100% 时), **只能靠 f≤5% 或"发热件移出贴皮肤区"**。
> **300mW 口径在这两个目标上的贡献 = 0**。
