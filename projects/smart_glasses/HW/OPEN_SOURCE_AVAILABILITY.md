## 1. 判据落地: 「开源数据」在本项目里到底指什么

**判据原文**: "优先使用开源数据更多的 sensor, 其他物料同理" (老板 11-02 09:23)

★**为什么这条判据在本项目不是锦上添花, 而是主判据之一**: 本项目主控是 **RK3572 (Rockchip)** ⇒ 采集链能不能跑起来, 取决于三样**软件资产**, 而这三样**都不是买硬件顺带送的**:

| 环节 | 需要什么 | 拿不到会怎样 |
|---|---|---|
| sensor 驱动 | V4L2 subdev 驱动 (寄存器时序 + 曝光/增益控制) | **RAW 都不出** ⇒ 后面全断 |
| ISP tuning | rkaiq 的 IQ 文件 (每个 sensor×镜头×模组一份 json) | 图像**能看但不能看** (色偏/噪点/暗角/白平衡全靠这文件) |
| 面板初始化 | DSI 面板的 init code + 时序 | **屏不亮/花屏** |

⇒ ★**"开源数据多"= 这三样东西里, 有多少是公开的、别人已经做过一遍的**。选料时它决定的是**能不能做出来 + 多久做出来 + 卡在谁手里**。

### 1.1 五个数据源 (可复算, 全部客观)

| 代号 | 数据源 | 为什么算它 | 快照文件 |
|---|---|---|---|
| **D1** | 上游 Linux 主线 `drivers/media/i2c/` | 通用性最好, 有了它 BSP 基本白送 | `linux_mainline_i2c.json` |
| **D2** | ★**Rockchip BSP kernel `drivers/media/i2c/` (develop-6.1, RK35xx 基线)** | ★**本项目实际编译的内核** —— D2 命中 = 驱动**直接可用** | `rockchip_bsp_i2c.json` |
| **D3** | rkaiq `iqfiles/` (isp3x / isp32 / isp32_lite) | ISP tuning 能不能**白嫖** | `rkaiq_iqfiles.json` |

## 3. ★★ 三条必须一起讲的结论 (只讲"3 vs 0"会误导)

### 3.1 结论一: **按老板判据 ⇒ ISS-138 选 D (AR0234CS)**

- 开源数据 **3/10 vs 0/10**, 且差距是**结构性的** (0 个仓库 vs 20 个仓库; 有公开规格库条目 vs 连条目都没有), 不是"多几个 star"的量差。
- 老板的判据是"**优先**使用开源数据更多的 sensor" ⇒ **D 胜出**。
- ★**代价 (要认)**: ①**破 §0 变量 30「豪威优先」** (供应链/成本/议价层面的代价, **不是技术不可行**) ②**16:10 vs 16:9** ⇒ 显示侧要 letterbox 或裁切 (已算: 立体角只丢 **9.70%**) ③**镜头靶面/焦距要重对** (AR0234CS 1/2.6" 3.0µm vs OV04C10 1/3" 1.998µm)。

### 3.2 结论二: ★**C 路真正的风险不是"生态差", 是"驱动要等谁给"**

- **C 路 = 从零写驱动**: 全网零实现 ⇒ 寄存器时序、曝光/增益/HDR 控制只能从**豪威**拿 ⇒ ★**豪威的寄存器文档/驱动常带 NDA, 且我们的问询单 (TBD-03) 目前还没拿到 lane 数/速率** ⇒ ★**如果豪威给不出寄存器表, C 路直接死, 而不是"慢一点"**。
- **D 路 = 移植**: 已有 GPL-2.0 完整驱动 (42KB) + DT overlay + RK3588 同族 bringup ⇒ 移植到 RK3572 rkisp3 是**工程活**, 不是"等外部"的活。
- ⇒ ★**这条判据真正改变的是"卡在谁手里"**: C 卡在豪威回信 (外部, 周期不可控), D 卡在我们自己 (内部, 可排期)。

### 3.3 结论三: ★★ **两个候选都没有现成 ISP tuning** ⇒ "选生态成熟的"在 tuning 这一层**不成立**

- rkaiq 公开 `iqfiles/isp3x` 与 `isp32` 目录里, ★**ov04c10 与 ar0234 都没有** (有的是 imx415 / imx327 / imx464 / os04a10 / ov02b10 / gc8034 / sc200ai 等)。
- ⇒ ★**不管选 C 还是 D, ISP tuning 都是项目内必须自己做的一笔账**: 需 RKISP Tuner + 暗室/灰卡 + 镜头/模组定版 ⇒ **估 1~2 人周 + 硬件调试窗口**, 且**必须等镜头与模组定版才能开始** (IQ 文件是 sensor×镜头×模组三者绑定)。
- ⇒ ★**这给老板一个真正的二选一之外的选项**: ★**若把 ISP tuning 外包/买现成 IQ (模组厂/调像服务商)**, 则 D 路"零 tuning 起点"的劣势消失, 而 C 路"零驱动起点"的劣势**无法外包** ⇒ ★**D 的相对优势进一步扩大**。
- ⇒ ★**同时, 这条也是本项目第一次把"ISP tuning 工作量"从隐性变成显性** —— 建议在 `HW/POWER_BUDGET_V3.md` 之外单独立一条内部工作项 (**ISP tuning 不占功耗但占人天与样机窗口**)。

### 3.4 判据管不到的: **指标本身**

开源数据判据**只回答"能不能做出来/多久做出来"**, 不回答"指标好不好" ⇒ C/D 的指标差仍然存在:

| | C (OV04C10+短镜头) | D (AR0234CS) |
|---|---|---|
| 角分辨率 | **0.1887 °/px** (比基线差 2.32×) | **0.1111 °/px** |
| 立体角损失 | 0% | 9.70% |
| 快门 | 滚动 | ★**全局** |
| ISP 吞吐余量 | 50.2% | 44.7% |

⇒ ★**D 在指标上也不差** ⇒ ★**"开源数据更多"与"指标更好"在 D 这边是同向的, 不存在取舍** ⇒ ★**这条判据是"白送"的加分, 不是"用指标换开源"**。

## 4. ★★ 其他物料同规则扫描 (老板: "其他物料同理")

**扫描口径**: 对每个关键物料问三个问题 —— ①它有没有"开源数据"这个维度 (即: 是不是要写驱动/初始化/tuning) ②现状有多少 ③这条判据会不会改变选型。

| 物料 | 有无开源数据维度 | 现状 (公开可得) | 本判据的处置 |
|---|---|---|---|
| ★**sensor** | ★**有 (驱动 + IQ)** | ★**C 路 0/10 · D 路 3/10** | ★**已改变选型 ⇒ 走 D** |
| **显示面板 视涯 0.49" SiOLED** | ★**有 (DSI init code + 时序)** | ★公开驱动/初始化序列 **0** (只能靠模组厂/面板厂给) | ⚠️ **红旗**: 与 sensor 同类风险 (外部依赖) ⇒ 但面板厂通常随模组提供 init code ⇒ **不改变选型, 但必须把 init code 写进 RFQ 硬判据** |
| **主控 RK3572** | 有 (ISP tuning + 平台 BSP) | 通用 BSP kernel 6.1 **公开** ✔ · rkaiq **公开** ✔ · ★**RK3572 专属 BSP/ISP tuning 不公开** (GitHub 搜 `rk3572` 仅 1 个无关仓库) | ⚠️ **红旗**: ISP tuning 必须在 RK3572 上做 ⇒ 与 §3.3 同一笔账, 不重复计 |
| **镜头 (120° 鱼眼, 定制)** | 无 (纯光学件) | 0 公开数据 | 该判据**不适用** ⇒ 走 RFQ + 模组厂 + 原厂 ISP tuning 周期 (已在 `HW/LENS_SELECTION.md`) |
| **充电 IC (BQ25896) / 电池保护 (BQ2970)** | 无 (I2C 器件, 无驱动) | TI 参考设计/数据手册**公开** ✔ | 该判据**不适用** ⇒ 仍按成本/交期/阈值参数判 |
| **连接器 (跨铰链 18p/16p) / 电池 / 波导 / 结构件** | 无 | 公开规格书部分可得 | 该判据**不适用** |

⇒ ★★ **本轮扫描的三条结论**:
1. ★**全项目只有 3 个物料存在"开源数据"维度: sensor · 显示面板 · 主控 ISP tuning** ⇒ ★**这条判据能改变选型的, 本轮只有 sensor 一个** (已落 D)。
2. ★**显示面板与主控各留一个红旗**: 面板 init code 与 RK3572 ISP tuning 都得**外部给/自己做** ⇒ 建议把这两条挂进 RFQ 与内部工作项, 别再靠"默认对方会给"。
3. ★**其余物料 (镜头/电源/连接器/结构件) 该判据不产生排序** ⇒ 继续按既有判据 (成本/交期/工艺/热) 走 ⇒ ★**这条新判据不是要替换别的判据, 是加在硬件/软件交界那一层的判据**。
